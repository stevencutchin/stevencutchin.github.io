Reverse-engineer the ER diagram

You are handed a written description of a real database. Your job is to turn it back into the diagram the designers drew — entities, keys, foreign keys, and crow's-foot cardinalities.

The mini-world

A company runs an automated website-privacy scanner. Customers register the sites they own; the service crawls each site's pages, runs scans, and records every privacy-relevant thing it finds — cookies, third-party trackers, browser-fingerprinting scripts, session recorders, keylogging listeners — plus a summary of the site's network traffic. It then generates reports and bills for the work.

One design decision is baked into the whole schema: every table except import_batch stores a site_id that points back to the owning site. It is deliberately denormalized — the same site you could reach by walking the parent chain, copied onto each row — so that any “everything for this site” query stays a single-column filter instead of a long chain of joins. You will represent this on your diagram.

Notation to use

Draw a crow's-foot ER diagram. One box per entity, listing its attributes; mark the primary key, add the foreign-key columns the rules below imply, and connect related entities with a line whose ends show the cardinality:

bar = the one end crow's foot = the many end ◆ primary key ○ foreign key ··· optional (nullable) link

Business rules (how the entities relate)

Each rule becomes one connector on your diagram. Read every rule in both directions to fix the cardinality before you draw it. “May” / “optional” means the link is nullable — draw it dashed.

1An import_batch brings in many sites; each site was brought in by one batch.
2A site has many urls; each url belongs to one site.
3A url can be the target of many scan_runs; each scan_run targets at most one url (optional).
4A scan_run contains many scans; each scan belongs to one run.
5A scan produces many findings of each of the six finding types; every finding was produced by one scan. (Six connectors, one per finding table.)
6A scan has at most one scan_summary, and a scan_summary describes exactly one scan. (What cardinality is that? Look at its primary key.)
7A scan produces at most one network_trace; each network_trace summarizes one scan.
8A network_trace has many network_trace_requests; each request belongs to one trace.
9A report may reference one scan_run and/or one scan it was built from (both optional), and may be derived from one earlier report (optional). So report also relates to itself.
10An invoice may reference one report (optional); a report can have many invoices.
11Denormalized site_id: every entity except import_batch carries a site_id foreign key to site. Add it to each box.

Your task

Deliverable (≈ 20–25 min, in pairs)

  1. Draw all sixteen entity boxes with their descriptive attributes; mark each primary key.
  2. Add the foreign-key column(s) each rule implies (e.g. url_id, scan_run_id, scan_id, network_trace_id, report_id, source_report_id, and site_id almost everywhere).
  3. Connect related entities with crow's-foot lines; put the bar on the one end and the crow's foot on the many end.
  4. Draw optional (nullable) links dashed.

Watch for these — they're the interesting parts

  • A 1:1 you can spot from the key. scan_summary uses scan_id as its primary key, so it can extend at most one scan — a one-to-one, not one-to-many.
  • A self-relationship. report can point at another report (source_report_id). One entity, both ends of the line.
  • Repeated structure. The six finding_* tables are the same shape with different payload columns — each connects to scan identically.
  • Optional vs. mandatory. Which links are nullable? A scan_run without a url, a report without a scan, an invoice without a report — all allowed.
  • Denormalization on purpose. Why copy site_id onto every table when the join chain already reaches site? What does it cost, and what does it buy? (Discussion.)

Instructor notes

The completed target diagram is in the companion file er-exercise-scanner-key.html (16 tables; open full-width or print landscape).

  • Structural chain: import_batch → site → url → scan_run → scan → the six findings; all one-to-many.
  • Cardinalities to check: Rule 6 is 1:1 (PK = FK); Rule 7 is 1:(0..1); Rule 9 yields three separate optional links into report, one of them recursive.
  • Grading surface: correct crow's-foot direction on every link, the 1:1 recognized, the recursive report link drawn, and site_id present on all but import_batch. The denormalization “why” is the discussion payoff, not a drawing requirement.
  • To shorten: assign only Intake + Scanning + Findings (rules 1–6) and treat traces/reports/billing as an extension.
