1 · What you are building, and why

Every topic in this course so far has been practiced in isolation: you drew ER diagrams on paper, mapped them to relations on paper, and wrote SQL against a database someone else had already created. This project is where those pieces become one system.

You will build a gradebook manager: a command-line application, written in Java, that stores everything it knows in a MySQL database running on your own machine. An instructor should be able to start your program, create a class, define grading categories and assignments, enroll students, record grades, and print a gradebook — and then quit, restart, and find everything exactly as they left it, because none of it ever lived in Java memory.

That last point is the whole exercise. The natural instinct of a Java programmer is to load everything into ArrayLists and HashMaps, compute in Java, and treat the database as a place to dump objects. Doing that here will cost you a substantial number of points. The database is not storage behind your application; it is your application's model. Your Java code is a thin shell that parses commands, sends SQL, and formats what comes back.

The shape of the system. Everything you are graded on for correctness happens on the right; Java is the part that asks the questions.

What this project assesses

  • Unit 1–2 — conceptual design and ER-to-relational mapping (Parts 1 and 2).
  • Unit 4 — SQL, including aggregation, grouping, joins, and views (Parts 2 and 4).
  • Unit 5 — application access via JDBC, prepared statements, and SQL injection (Part 3).
  • Unit 7 — index selection and physical design (Part 2, and Part 6 for CS 510).

2 · The problem domain

Read this section as a requirements document from a client. Each requirement is labelled (D1, D2, …) so you can refer to it in your design write-up and so we can refer to it when grading. The requirements describe what must be true, not what tables to create — the mapping is your job.

D1 · Classes

The system tracks many classes. A class is identified to a user by its course number (e.g. CS410), term (e.g. Fa26), and section number (e.g. 1). No two classes share all three. A class also has a description (e.g. Databases). You may add fields you can justify.

D2 · Categories

A class has one or more grading categories — homework, exam, project, participation, and so on. Each category has a name and a weight. Category names are unique within a class, and two different classes may use different category names and weights. Weights are not required to sum to 100; see D8.

D3 · Assignments

A class has assignments. Each belongs to exactly one category of that class, and has a name, a description, and a point value (the maximum points available). No two assignments in the same class may share a name; assignments in different classes may.

D4 · Students

A student has a username (the part of their email address before the @), a student ID, and a name. A student exists independently of any class and may be enrolled in many classes across many terms. Usernames and student IDs are each unique across the whole system.

D5 · Enrollment

A student is enrolled in zero or more classes; a class enrolls zero or more students. A student cannot be enrolled in the same class twice.

D6 · Grades

A student who is enrolled in a class may be assigned a grade — a number of points — for an assignment in that class. A student has at most one grade per assignment. A student with no grade for an assignment is ungraded, which is not the same as scoring zero: the distinction drives §4's two grade figures, so do not represent it with a 0.

D7 · Grade integrity

It must be impossible for the database to hold a grade for a student who is not enrolled in the class that owns the assignment. Enforce this with constraints where you can; where the constraint cannot be expressed declaratively, say so in your README and explain how your application prevents it.

D8 · Grade calculation

Grades are reported out of 100 using the weighted scheme fully specified in §4.

3 · Deliverables

Part 1 — Conceptual and logical data model

Produce a single PDF, model.pdf, containing:

  • An ER or EER diagram covering D1–D7, in either Chen or Elmasri–Navathe notation. Show cardinality ratios, participation constraints, keys, and any weak entities. State which notation you used.
  • The relational schema diagram that your ER model maps to: relation names, attributes, primary keys underlined, and foreign-key arrows.
  • Half a page of prose naming the design decisions you actually had to make — for example, how you represented a category's relationship to a class, or how you guaranteed D7. Two defensible models of the same requirements are both acceptable; an undefended one is not.

Part 2 — MySQL schema

Produce schema.sql: a script that creates your database from nothing. It must run cleanly on a fresh MySQL server with mysql < schema.sql and must include:

  • CREATE TABLE statements with appropriate data types. Use DECIMAL for point values and grades, not FLOAT or DOUBLE.
  • PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, and CHECK constraints implementing D1–D7. Choose ON DELETE / ON UPDATE behavior deliberately for each foreign key.
  • At least two secondary indexes beyond those created automatically by keys, each with a one-line comment in the script saying which query it is there to serve.
  • Any views you use. Views are encouraged for the reporting queries in §4.

Part 3 — Java command-shell application

A Java program that presents an interactive prompt, reads one command per line, executes it against MySQL, prints the result, and loops until the user exits. The full command reference is §5.

Part 4 — SQL-first computation

This is a requirement on how Part 3 is implemented, and it is graded separately. Do the work in SQL. Specifically:

  • student-grades must be produced by one query (a view or CTE chain counts as one), and gradebook by one more.
  • Java may loop over the result set to format output. Java must not compute sums, averages, weights, or rescaling.
  • Every value that came from user input must reach the database through a PreparedStatement parameter. String concatenation into SQL anywhere in your source is an automatic deduction, whether or not it is exploitable.

Part 5 — Documentation and demonstration

A README.md and a demonstration video; see §10.

Part 6 — CS 510 only

A performance and indexing analysis, plus an in-class presentation; see §12.

4 · Grade calculation, specified exactly

The old version of this project left this section vague, and every team interpreted it differently. It is now pinned down. Implement exactly this.

Definitions

For a given student in a given class:

  • A category's possible points is the sum of the point values of all assignments in that category.
  • A category's attempted points is the sum of the point values of the assignments in that category for which the student has a grade.
  • A category's earned points is the sum of the student's grades in that category.

Two figures, always reported together

  1. Total grade — what the student has now, treating everything not yet graded as worth zero. Each category's fraction is earned ÷ possible.
  2. Attempted grade — how the student is doing on the work they have actually been graded on. Each category's fraction is earned ÷ attempted.

Weight rescaling

Category weights are rescaled to sum to 100 before use. If the categories carry weights 40, 40 and 30, they contribute 36.36, 36.36 and 27.27 respectively.

The three edge cases that decide this section's points

  • A category with no assignments has no possible points. Exclude it from both figures and rescale the remaining weights over the categories that remain.
  • A category with assignments but none attempted is excluded from the attempted grade only, and the remaining weights are rescaled again for that figure. It stays in the total grade, contributing zero.
  • A student with no grades at all has a total grade of 0.00 and an attempted grade that is undefined. Print — or n/a, not 0.00.

Round only at the point of display, to two decimal places. Do not round intermediate values.

5 · Command reference

Your shell must implement every command below. Arguments in <angle brackets> are required, [square brackets] optional. Any argument that may contain spaces is given in double quotes on the command line; your parser must handle quoted arguments.

After select-class, every subsequent command operates on the selected class — the same way a shell's working directory scopes the commands you type. Any class-scoped command issued with no class selected must print an error, not crash.

Class management

CommandBehavior
new-class <course> <term> <section> "<description>" Creates a class. Example: new-class CS410 Fa26 1 "Databases". Error if that course/term/section already exists.
list-classes Lists every class with its course number, term, section, description, and the number of students enrolled. Order by term then course number.
select-class <course> [<term>] [<section>] Makes a class active. With only a course number, selects that course's single section in the most recent term — and fails with a message listing the candidates if there is more than one. With course and term, same rule within that term. With all three, selects exactly that section.
show-class Shows the active class and its enrollment count, or reports that no class is selected.

Categories and assignments

CommandBehavior
show-categories Lists the active class's categories with their weights, and the rescaled percentage each one is worth.
add-category <name> <weight> Adds a category to the active class. Error if the name is already used in this class, or the weight is not a positive number.
show-assignments Lists the active class's assignments grouped by category, with point values, plus each category's total possible points.
add-assignment <name> <category> <points> "<description>" Adds an assignment. Error if the name is already used in this class, if the category does not exist in this class, or if points are not positive. Note the argument order differs from earlier versions of this assignment — the quoted description is last.

Students and grades

CommandBehavior
add-student <username> <student-id> <last> <first> Creates the student if they do not exist, then enrolls them in the active class. If the student already exists and the supplied name differs from the stored name, update the stored name and print a warning showing the old and new values. Error if already enrolled in this class.
add-student <username> Enrolls an existing student in the active class. Error if no such student exists — do not create one from a bare username.
show-students [<string>] With no argument, lists all students in the active class. With a string, lists those in the active class whose username or name contains it, case-insensitively.
grade <assignment> <username> <points> Records a grade, replacing any existing grade for that student and assignment. Error if the assignment is not in the active class, or the student is not enrolled in it. If the points exceed the assignment's point value, record it anyway but print a warning showing the configured maximum. Negative points are an error.

Reporting

CommandBehavior
student-grades <username> For one student in the active class: every assignment, grouped by category, showing the grade or a clear ungraded marker; a subtotal per category with its weight; and the total and attempted grades from §4.
gradebook Every student in the active class — username, student ID, name — with their total and attempted grades. Order by last name.

Shell commands

CommandBehavior
help [<command>] Lists the commands, or explains one of them.
quit  ·  exit Closes the connection cleanly and exits with status 0. End-of-input (Ctrl-D) behaves the same way.

You may add commands beyond these — drop-student, delete-assignment, import-students from a CSV, and so on. Document any you add in your README. Extra commands do not earn extra points, but a shell that is pleasant to use does help the demonstration go well.

Behavior expected of every command

  • No stack traces. Any error a user can cause — bad arguments, missing class, duplicate name, constraint violation — produces a one-line message beginning with error: and returns to the prompt. Catch SQLException and translate it.
  • No silent success. A command that changes data confirms what it did.
  • Multi-statement changes are atomic. Where a command performs more than one write, wrap it in a transaction and roll back on failure.
  • Tabular output is aligned. Use String.format or equivalent; do not print raw toString() output.

6 · Environment and technical requirements

  • Database: MySQL Community Server, installed and running on your own machine. MySQL 9.7 LTS is the reference version; 8.4 LTS is also fine. Docker is an acceptable way to run it. Do not build against a shared server — your submission must be reproducible from schema.sql and dump.sql alone.
  • Language: Java 21 or later. Java 25 (the current LTS) is recommended.
  • Driver: MySQL Connector/J, declared as a dependency (com.mysql:mysql-connector-j). Note the group ID — the old mysql:mysql-connector-java coordinates are deprecated.
  • Build: Maven or Gradle, so that a clean checkout builds with one command. A plain javac build is acceptable only if you include a working build script and vendored driver JAR.
  • Credentials: read the JDBC URL, username, and password from a configuration file or environment variables. Hard-coded passwords in source cost points. Include a config.properties.example with placeholder values, and make sure the real one is not in your submission.
  • Structure: separate the command parsing, the database access, and the output formatting. A single 900-line Main.java will be marked down under code quality.
