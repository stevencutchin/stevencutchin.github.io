Joins · 1

The FROM-clause join

List several tables in FROM and you get their Cartesian product; a WHERE condition on matching keys turns it into a join — exactly σ over ×.

Qualify shared column names with the table (or an alias) so the reference is unambiguous.

Forget the condition, get a product

Omit the WHERE join predicate and you get every pairing — a silent, enormous result. This is the classic runaway query.

-- each student with their courses
SELECT S.Name, E.CourseID, E.Grade
FROM   STUDENT S, ENROLLMENT E
WHERE  S.StudentID = E.StudentID;

Two tables in FROM, joined by the key match in WHERE.

Joins · 2

Explicit JOIN … ON

The modern form puts the join and its condition together, keeping the WHERE clause for genuine filtering:

  • INNER JOIN … ON — any condition.
  • NATURAL JOIN — auto-match on shared column names.
  • JOIN … USING (col) — match on a named shared column, keeping just one copy of it.

Same result as the FROM-clause form — clearer intent, and harder to forget the condition.

SELECT S.Name, C.Title, E.Grade
FROM   STUDENT S
  JOIN ENROLLMENT E ON E.StudentID = S.StudentID
  JOIN COURSE C     ON C.CourseID  = E.CourseID
WHERE  S.Major = 'CS';

Chained joins; WHERE is left to filter, not to join.

Joins · 3

Outer joins keep the unmatched

An inner join drops rows with no match. The LEFT, RIGHT, and FULL OUTER JOIN keep them, filling the missing side with NULL — the SQL form of ⟕ ⟖ ⟗.

"Every student, with courses if any" needs a LEFT join so Omar survives with NULLs.

SELECT S.Name, E.CourseID
FROM   STUDENT S
  LEFT OUTER JOIN ENROLLMENT E
       ON E.StudentID = S.StudentID;

Reads as

Ada→CS410, Liang→CS410, Grace→MATH301, and Omar→NULL. Try the explorer next slide.

Subqueries · 1

Nested subqueries (uncorrelated)

A subquery in WHERE computes a set of values the outer query tests against. Here it runs once — it doesn't depend on the outer row.

  • IN (subquery) — value is among the results.
  • NOT IN (subquery) — value is absent.

NOT IN and NULL

If the subquery yields any NULL, NOT IN can return no rows at all — three-valued logic again. Prefer NOT EXISTS when NULLs are possible.

-- students enrolled in CS410
SELECT Name FROM STUDENT
WHERE StudentID IN (
  SELECT StudentID FROM ENROLLMENT
  WHERE CourseID = 'CS410');

-- students never enrolled (Omar)
SELECT Name FROM STUDENT
WHERE StudentID NOT IN (
  SELECT StudentID FROM ENROLLMENT);

Subqueries · 2

Correlated subqueries & EXISTS

A correlated subquery references a column from the outer row, so it is re-evaluated per outer row.

EXISTS is true when the subquery returns at least one row — it tests presence, not values, and pairs naturally with correlation.

NOT EXISTS is the mirror: no matching row at all.

-- students who earned an A somewhere
SELECT S.Name
FROM   STUDENT S
WHERE EXISTS (
  SELECT * FROM ENROLLMENT E
  WHERE  E.StudentID = S.StudentID
    AND  E.Grade = 'A');

The inner E references the outer S — that's the correlation.

Subqueries · 3

Quantified comparison: ANY, ALL

Compare a value against a whole set of subquery results:

  • > ANY (…) — greater than at least one (i.e. greater than the minimum).
  • > ALL (…) — greater than every one (greater than the maximum).
  • = ANY is just IN.
-- courses more popular than every
-- Math course (by enrollment count)
SELECT CourseID FROM ENROLLMENT
GROUP BY CourseID
HAVING COUNT(*) > ALL (
  SELECT COUNT(*) FROM ENROLLMENT
  WHERE CourseID LIKE 'MATH%'
  GROUP BY CourseID);

GROUP BY / HAVING arrives fully next lecture — here just for the ALL.

Subqueries · 4 — the hard one

"For all" — division via NOT EXISTS

SQL has no direct division operator. Express "for all" by the double negative: a student took every required course when there is no required course they did not take.

The two nested NOT EXISTS are the pattern to recognize — it's the algebra's ÷ written in SQL.

Read it inside-out

Inner: a required course with no matching enrollment. Outer: keep the student for whom that inner set is empty.

-- students who took ALL required courses
SELECT S.Name FROM STUDENT S
WHERE NOT EXISTS (
  SELECT * FROM REQUIRED R
  WHERE NOT EXISTS (
    SELECT * FROM ENROLLMENT E
    WHERE E.StudentID = S.StudentID
      AND E.CourseID  = R.CourseID));

Modifying data · 1

INSERT

Add rows with an explicit column list — always list the columns, so the statement survives a later schema change.

You can insert several rows at once, or feed rows straight from a query with INSERT … SELECT.

Constraints still apply

Every INSERT is checked against PK, FK, NOT NULL, and CHECK. A missing column takes its DEFAULT, or NULL if none is set.

INSERT INTO STUDENT (StudentID, Name, Major)
VALUES ('S1005', 'Nadia Rahman', 'CS');

-- rows straight from a query
INSERT INTO HONORS (StudentID, Name)
SELECT StudentID, Name FROM STUDENT
WHERE  Major = 'CS';

Modifying data · 2

UPDATE & DELETE

UPDATE changes columns in the rows a WHERE clause selects; DELETE removes them.

The WHERE clause is the same selection σ as in a query — it decides which rows are affected.

The missing WHERE

No WHERE means every row. An UPDATE or DELETE without one rewrites or empties the whole table. Check twice.

UPDATE STUDENT
SET    Major = 'Data Science'
WHERE  StudentID = 'S1004';

DELETE FROM ENROLLMENT
WHERE Grade IS NULL;

A DELETE can cascade to dependents if the FK said so.

Judgment

Pitfalls & tips

  • A missing join predicate is a product. Every extra table in FROM needs a matching condition, or the row count explodes.
  • Inner joins hide the unmatched. If you need students with no enrollment, that's a LEFT join, not an inner one.
  • NOT IN breaks on NULL. A single NULL in the subquery can zero out the result. Reach for NOT EXISTS.
  • "For all" is two NOT EXISTS. Whenever a question says "every" or "all," think division, not join.
  • UPDATE/DELETE without WHERE hits everything. Preview with a SELECT on the same WHERE before you run it.
