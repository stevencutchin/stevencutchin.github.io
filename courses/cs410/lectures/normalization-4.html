The standard every split must meet

Two properties a decomposition must earn

Lossless join

  • Rejoining the pieces gives back exactly the original relation.
  • No spurious tuples — no invented rows.
  • Non-negotiable. A lossy split corrupts the data.

Dependency preservation

  • Every FD can be checked on a single relation, no join needed.
  • Keeps constraint enforcement cheap.
  • Desirable, but sometimes traded away (recall BCNF).

Lossless is mandatory; dependency preservation is the one we sometimes can't have alongside BCNF.

Property 1 · the test

Testing for a lossless join

For a decomposition of R into two relations R1 and R2, the join is lossless iff their shared attributes form a key of at least one side:

(R1 ∩ R2) → R1  or  (R1 ∩ R2) → R2

In words: the common column(s) must determine everything in one of the two relations. Compute the closure of the intersection to check.

Why it works

If the shared attribute is a key of R2, each row of R1 matches exactly one row of R2 — so the join can't multiply rows or invent new ones.

Property 1 · the failure

Spurious tuples — the lossy failure

When the shared attribute is not a key of either side, the rejoin matches rows that don't belong together and manufactures tuples that were never in R.

Those extra rows are spurious tuples. They don't just add noise — they represent facts the database never held, silently corrupting every query that joins.

The rule of thumb

Split on a key, and you're safe. Split on a non-key common attribute, and expect spurious tuples. The interactive shows both.

Property 1 · beyond two relations

More than two pieces: the chase

The key-of-one-side test is for a binary split. For a decomposition into three or more relations, use the chase algorithm.

Build a tableau — one row per relation, matching symbols on shared attributes — then repeatedly apply the FDs to equate symbols. If some row becomes all-original, the decomposition is lossless.

You mostly won't hand-run it

Both BCNF decomposition and 3NF synthesis are constructed to be lossless, so you rarely need the chase in practice. Know it exists and what it decides.

Property 2 · the test

Testing dependency preservation

Project the FDs onto each relation — the FDs whose attributes all fit inside that relation. The decomposition is dependency-preserving when the union of those projections is equivalent to the original F.

Equivalent, checked with closures: every original FD must follow from the projected ones.

What loss looks like

If an FD's attributes are split across two relations and it can't be re-derived from the projections, it's lost — enforcing it now requires a join. That was the BCNF/TEACH situation exactly.

Two strategies

Two ways to build a good schema

Decomposition (top-down)

  • Start with one big relation; split on each violating FD.
  • Target: BCNF.
  • Always lossless.
  • Dependency preservation not guaranteed.

Synthesis (bottom-up)

  • Start from a minimal cover; build relations up from the FDs.
  • Target: 3NF.
  • Always lossless and dependency-preserving.
  • Guaranteed 3NF, not always BCNF.

Want all three guarantees at once? Synthesis to 3NF is the one that delivers them.

The synthesis procedure

The 3NF synthesis algorithm

  1. Compute a minimal cover G of F.
  2. For each left side X in G, make a relation with X and all attributes X determines (group FDs by common left side).
  3. If no relation contains a candidate key of the original R, add one relation that is a candidate key.
  4. Drop any relation whose attributes are a subset of another's.

The guarantee

The result is in 3NF, is a lossless decomposition of R, and preserves every dependency — the theoretical best you can promise for 3NF. This is why we computed a minimal cover last lecture.

Beyond functional dependencies

Multivalued dependencies (MVD)

Some redundancy survives BCNF because it isn't caused by an FD at all. When an entity has two independent multivalued facts, storing them in one relation forces every combination.

An MVD X ↠ Y holds when the set of Y-values for an X is independent of the other attributes.

The MVD normal form

Fourth normal form (4NF)

4NF

A relation is in 4NF when, for every nontrivial MVD X ↠ Y, X is a superkey.

The fix mirrors the FD case: split the independent facts into separate relations.

And 5NF, briefly

5NF (project–join normal form) handles the rare case where a relation must be split into three or more pieces to avoid spurious tuples — a join dependency not implied by any key. Real, but you'll seldom meet it. 4NF is the practical ceiling.

The whole ladder at a glance

2NFno partial FD on a key

4NFevery MVD determinant is a superkey

Each implies the ones above it. Most designs target 3NF or BCNF; reach for 4NF when independent multivalued facts collide.

Judgment in practice

When to stop — and even step back

Normalization removes redundancy by adding relations — and joins. Sometimes, for a read-heavy workload, the join cost outweighs the anomaly risk.

Denormalization deliberately reintroduces some redundancy for performance — after measuring, and with a plan to keep the copies consistent (triggers, materialized views).

Do it on purpose, not by accident

Normalize first so you understand the dependencies; denormalize second, as a conscious, measured trade. An un-normalized schema you never reasoned about is a bug, not an optimization.

Judgment

Pitfalls & tips

  • Lossless is not optional. Always verify the shared attribute is a key of one side before trusting a binary split.
  • Spurious tuples are silent. A lossy schema looks fine until a join returns rows that were never stored.
  • Synthesis when you need all three guarantees. 3NF synthesis gives lossless + dependency-preserving + 3NF together.
  • MVDs aren't FDs. If BCNF still shows combinatorial repetition, look for an independent multivalued fact and go to 4NF.
  • Denormalize deliberately. Only after measuring, and only with a consistency mechanism for the duplicated data.
