Stored procedures · motivation

Why put logic in the database?

A stored procedure is code that lives and runs on the database server. Reasons to move logic there:

  • Fewer round-trips — a multi-step operation runs in one call.
  • Shared logic — every app (Java, Python, a report tool) calls the same rule.
  • Encapsulation & security — grant EXECUTE on the procedure, not raw table access.

The trade-offs

Procedural SQL is less portable across vendors, harder to unit-test and version than application code, and can hide business logic where developers don't look. Use it where its strengths clearly win.

Stored procedures · 1

CREATE PROCEDURE & CALL

A procedure has a name, typed parameters, and a body. Parameters carry a direction:

  • IN — passed into the procedure.
  • OUT — returned back to the caller.
  • INOUT — both.

Invoke with CALL.

CREATE PROCEDURE course_count(
  IN  sid CHAR(5),
  OUT n   INT)
BEGIN
  SELECT COUNT(*) INTO n
  FROM ENROLLMENT
  WHERE StudentID = sid;
END;

CALL course_count('S1001', @c);

Stored procedures · 2

SQL/PSM — a real programming language

SQL/PSM (Persistent Stored Modules) adds the procedural pieces SQL lacks: local DECLARE variables and control flow — IF, CASE, WHILE, LOOP, FOR.

A function returns a value, so it can be used inside a query — a computed column with a name.

CREATE FUNCTION standing(g DECIMAL(3,2))
  RETURNS VARCHAR(10)
BEGIN
  IF g >= 3.5 THEN RETURN 'Honors';
  ELSEIF g >= 2.0 THEN RETURN 'Good';
  ELSE RETURN 'Warning';
  END IF;
END;

SELECT Name, standing(GPA) FROM STUDENT;

Stored procedures · 3

A cursor inside a procedure

The cursor loop from last lecture, now living server-side. A handler catches the "no more rows" condition and ends the loop cleanly.

This flags every student carrying more than six courses — a rule that would take several round-trips from the application, done in one call.

CREATE PROCEDURE flag_overload()
BEGIN
  DECLARE done INT DEFAULT 0;
  DECLARE sid CHAR(5); DECLARE cnt INT;
  DECLARE c CURSOR FOR
    SELECT StudentID, COUNT(*) FROM ENROLLMENT
    GROUP BY StudentID;
  DECLARE CONTINUE HANDLER FOR NOT FOUND
    SET done = 1;
  OPEN c;
  loop: LOOP
    FETCH c INTO sid, cnt;
    IF done THEN LEAVE loop; END IF;
    IF cnt > 6 THEN
      INSERT INTO OVERLOAD VALUES(sid);
    END IF;
  END LOOP;
  CLOSE c;
END;

Stored procedures · 4

Function or procedure?

FunctionReturns one value; callable inside a query. Should be deterministic and side-effect-free.
ProcedureDoes work via OUT parameters and side effects; called with CALL, not inside a SELECT.
TriggerProcedure-like body the DBMS fires automatically on an event (Unit 4). Not called directly.

Rule of thumb

If you want to use the result in SQL, write a function. If you want to perform an operation — insert, update, multi-step work — write a procedure. Keep functions pure so the optimizer can trust them.

Security · the setup

The code–data boundary

Every query the database runs is code. When an application builds that code by pasting user input into a string, it hands the user a chance to write code too.

The whole of SQL injection is that one confusion: input meant to be data gets parsed as SQL. Keeping the two apart is the entire defense.

Where it lives

Anywhere a query is assembled with string concatenation and untrusted input — a login form, a search box, a URL parameter, an API field. This is consistently among the most damaging web vulnerabilities.

Security · the vulnerability

How injection happens

Consider a login that builds its query by concatenation:

The developer intends the input to be a username. But the string is handed to the parser whole — so characters like a quote can close the literal early and let the rest be read as SQL.

// VULNERABLE: input pasted into SQL text
String sql =
  "SELECT * FROM USERS " +
  "WHERE user='" + user +
  "' AND pass='" + pw + "'";
st.executeQuery(sql);

The quotes that were meant to fence the value can be supplied by the value.

Security · the textbook case

The classic login bypass

Supply a password of ' OR '1'='1. Concatenated in, the WHERE clause becomes a tautology — always true — so the check passes without a valid credential.

The same trick shape (a broken-out quote plus injected SQL) can read or destroy data, not just skip a login. One flaw, wide blast radius.

// pass = ' OR '1'='1
SELECT * FROM USERS
WHERE user='alice'
  AND pass='' OR '1'='1';
// '1'='1' is always true → row returned

The injected fragment turns the condition into "always true."

Check yourself · interactive

Same malicious input, two constructions

The attacker types ' OR '1'='1 in the password box. Watch what the database actually receives under each approach.

Ordinary input: pass = 'secret'. Concatenated, the query checks user and password normally and matches Alice's one row. Login succeeds as intended.

SELECT * FROM USERS
WHERE user='alice' AND pass='secret';

Login OK — matches Alice's single row, as intended.

SELECT * FROM USERS
WHERE user='alice' AND pass='' OR '1'='1';

Bypassed — the condition is always true; every row matches.

SELECT * FROM USERS
WHERE user=? AND pass=?;
// ?2  ←  "' OR '1'='1"   (one literal value)

Login refused — no user has that literal password; the input never becomes SQL.

Security · the fix

The fix: parameterized queries

Send the DBMS a fixed statement with placeholders, then bind values separately. A bound value is never parsed as SQL — it can't add a clause, close a quote, or change the statement's structure.

This is the prepared statement from last lecture, now doing security work as well as performance work.

// SAFE: structure fixed, values bound
PreparedStatement ps = con.prepareStatement(
  "SELECT * FROM USERS " +
  "WHERE user=? AND pass=?");
ps.setString(1, user);
ps.setString(2, pw);   // input stays data
ResultSet rs = ps.executeQuery();

The rule

Never build SQL by concatenating input. Bind it.

Security · layers

Defense in depth

Parameterization is the primary fix. Layer more behind it, because no single control should be load-bearing alone:

  • Least privilege — the app's DB account can touch only what it needs; no DROP, no admin.
  • Input validation — accept known-good shapes (an allowlist), as a complement, not a replacement.
  • Views & procedures — expose a narrow, parameterized surface.

What doesn't work

Hand-escaping quotes and blocklisting "bad words" are fragile — attackers find encodings and edge cases you didn't. Parameterize instead of trying to sanitize your way to safety.

Bringing the halves together

Procedures don't automatically save you

Stored procedures can reduce the attack surface — but only if they themselves use parameters. A procedure that builds dynamic SQL by concatenation inside its body is just as injectable.

The lesson unifies the lecture: wherever SQL text is assembled from input — in the app or in the database — bind, don't concatenate.

-- Still vulnerable: concatenation inside
SET @q = CONCAT(
  'SELECT * FROM STUDENT WHERE Name=''',
  term, '''');
PREPARE s FROM @q; EXECUTE s;

-- Safe: a parameter marker
PREPARE s FROM
  'SELECT * FROM STUDENT WHERE Name=?';
EXECUTE s USING term;

Judgment

Pitfalls & tips

  • Concatenated input is the vulnerability. If user data reaches a query as string text, assume it's exploitable.
  • Parameterize everywhere — in the app and in any dynamic SQL inside procedures.
  • Validation complements, never replaces. Allowlists help; they are not a substitute for binding.
  • Grant the least the app needs. A compromised query does far less damage on a restricted account.
  • Weigh stored logic. Procedures buy fewer round-trips and central rules, at the cost of portability and testability.
