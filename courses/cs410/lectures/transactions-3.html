Other concurrency control

Three alternatives to locking

Timestamp orderingOrder transactions by a timestamp; abort any operation that would violate it. No locks, no deadlock.
Optimistic (validation)Run without checks, then validate at commit; roll back on conflict. Great when conflicts are rare.
Multiversion (MVCC)Keep several versions of each item so reads and writes rarely block each other. The modern default.

Same goal, different bet

All produce serializable schedules. Locking bets that conflicts are common; timestamps and optimistic control bet they're rare; MVCC sidesteps read–write conflicts entirely.

Ordering by age

Timestamp ordering

Each transaction gets a unique timestamp TS(T) when it starts. The protocol enforces that the schedule is equivalent to running the transactions in timestamp order.

Each data item X remembers two stamps:

  • read_TS(X) — the newest transaction that read X;
  • write_TS(X) — the newest that wrote X.

No locks at all

There's nothing to wait on, so deadlock is impossible. The cost moves to aborts: a transaction that arrives "too late" is restarted with a fresh timestamp.

The check on each operation

The basic TO rules

Before each operation, compare TS(T) with the item's stamps:

  • T reads X: allowed unless a younger transaction already wrote X (write_TS(X) > TS(T)) — then T is too late → abort.
  • T writes X: allowed unless a younger transaction already read or wrote X — then abort.

An aborted transaction rolls back and restarts with a new, larger timestamp.

Thomas's write rule

An obsolete write — one already overwritten by a younger transaction — can simply be ignored rather than causing an abort, improving concurrency without breaking serializability.

The modern default

Multiversion concurrency control

Instead of overwriting an item, MVCC keeps its old versions. A write creates a new version; a read is served the version that was current as of the reader's start.

So readers never block writers, and writers never block readers — each transaction sees a consistent snapshot of the database.

Snapshot isolation

This gives snapshot isolation, used by PostgreSQL, Oracle, and others. It's fast and avoids most anomalies — though plain snapshot isolation needs an extra check (write-skew) to be fully serializable.

Dialling concurrency up

SQL isolation levels

The SQL standard lets an application trade isolation for concurrency by choosing how much anomaly it tolerates.

Weaker levels run faster but permit more anomalies; only serializable forbids them all.

Surviving failure

Recovery — atomicity & durability

Concurrency control handled isolation. Recovery handles the rest: after a crash, the database must be restored to a state where every committed transaction is present and every uncommitted one is erased.

Failures to survive: a transaction error or abort, a system crash (power, OS), and media failure (disk loss, handled by backups).

The core problem

At the moment of a crash, some committed changes may not have reached disk, and some uncommitted ones may have. Recovery must sort out both — and the log is how.

The source of truth

The system log

The log is an append-only, on-disk record of every change, written as the transaction runs. Each write records the item's old and new values — enough to undo or redo it.

Because the log is durable and sequential, it's the authoritative history the recovery manager replays.

[start, T1]
[write, T1, X, old=5, new=8]
[commit, T1]
[start, T2]
[write, T2, Y, old=1, new=9]
— crash —

Old + new values let recovery go either direction.

The one rule that makes it work

Write-ahead logging (WAL)

The WAL rule: a change's log record must reach disk before the data page it describes — and all of a transaction's log records must be on disk before it can commit.

This guarantees that whatever the data pages look like after a crash, the log already contains enough to undo or redo them. Without WAL, a change could hit disk with no record of how to reverse it.

The two directions

Undo & redo

After a crash, recovery walks the log and applies two operations:

  • UNDO — for transactions that never committed, restore the old values, erasing their partial work (atomicity).
  • REDO — for committed transactions, reapply the new values in case they hadn't reached disk (durability).

Deferred vs immediate

If updates are deferred until commit, you only ever redo. If they're written immediately (the common case), you may need both — undo the losers, redo the winners.

Bounding the work

Checkpoints

Without help, recovery would scan the entire log from the beginning. A checkpoint periodically flushes dirty pages to disk and writes a checkpoint record to the log.

Recovery can then start from the last checkpoint: everything before it is already safely on disk, so there's no need to look further back.

Why it matters

Checkpoints turn recovery time from "proportional to the whole log" into "proportional to work since the last checkpoint" — the difference between minutes and hours after a crash.

The industry algorithm

ARIES — recovery in three passes

ARIES is the recovery algorithm real systems use. Built on WAL and per-record log sequence numbers (LSNs), it runs three passes over the log:

  1. Analysis — from the last checkpoint, find which transactions were active and which pages were dirty.
  2. Redo — repeat all logged changes to restore the exact pre-crash page state.
  3. Undo — roll back the transactions that never committed.

"Repeat history"

ARIES redoes everything first — even the losers' changes — then undoes the losers. Reconstructing the precise crash state before undoing is what makes it robust and restartable.

Judgment

Pitfalls & tips

  • Timestamp ordering trades deadlock for aborts. No waiting means no deadlock — but "too late" transactions restart, risking starvation.
  • MVCC ≠ automatically serializable. Snapshot isolation is fast but needs an extra check to catch write-skew.
  • Weaker isolation is a deliberate trade. Know which anomaly each level admits before choosing it.
  • WAL is non-negotiable. Log before data, and before commit — it's what makes undo and redo possible at all.
  • Checkpoints bound recovery time. Redo committed work since the checkpoint, undo the uncommitted — never rescan the whole log.
