The normal forms

Normalization II
1NF, 2NF, and 3NF

Last time we built the tools. Now we use them: a ladder of tests, each removing a specific kind of bad dependency and the anomalies it causes.

A relation climbs from 1NF to 2NF to 3NF by decomposition — splitting off the attributes that depend on the wrong thing.

The shape of the process

For each normal form: state a test on the FDs, check it, and if it fails, decompose so each piece passes. The forms nest — 3NF is stricter than 2NF is stricter than 1NF.

Orientation

A ladder of nested tests

Each normal form is a condition on a relation's dependencies. They stack: satisfying 3NF implies 2NF implies 1NF.

Our running example is one wide relation with both problems on display:

ENROLL(SID, CID, SName, CTitle, InsID, InsName, Grade)

Its FDs — from the meaning of the data:

SID → SName CID → CTitle, InsID InsID → InsName SID, CID → Grade

Key = {SID, CID}. Watch SName/CTitle (partial) and InsName (transitive).

The baseline · 1NF

1NF — atomic values only

A relation is in 1NF when every attribute value is atomic — no repeating groups, no set-valued or nested cells. It's the assumption the relational model already makes.

The fix for a repeating group is to give each value its own row, promoting the repeating attribute into the key.

Not 1NF — a set of courses in one cell

Toward 2NF · the concept

Partial dependencies

A partial dependency is when a nonprime attribute depends on part of a candidate key, not the whole thing.

It can only arise when the key is composite. With a single-attribute key there are no proper parts, so 1NF already gives you 2NF.

The tell

A fact that repeats identically across a key value is the signature of a partial dependency — SName is the same in every row for a given SID.

In ENROLL, key = {SID, CID}:

SID → SName (partial) CID → CTitle, InsID (partial)

SName needs only SID; CTitle and InsID need only CID. Neither needs the full key.

Toward 2NF · the rule

2NF — full dependency on the key

A relation is in 2NF when it is in 1NF and no nonprime attribute is partially dependent on any candidate key — every nonprime attribute needs the whole key.

ENROLL fails: SName, CTitle, and InsID each depend on only part of {SID, CID}. Only Grade depends on the full key.

How to fix it

For each partial dependency, move the determined attributes into a new relation keyed by the part they actually depend on. What genuinely needs the full key stays behind.

Toward 2NF · the result

Decomposing to 2NF

Split off each partially-dependent group by its own determinant:

STUDENT(SID, SName)
COURSE(CID, CTitle, InsID, InsName)still hides a transitive dependency — see 3NF
ENROLLMENT(SID, CID, Grade)Grade needs the whole key — stays

Progress, not done

All three are now in 2NF — no partial dependencies remain. But COURSE still carries InsID → InsName, a nonprime-to-nonprime dependency. That's the next rung.

Toward 3NF · the concept

Transitive dependencies

A transitive dependency is when a nonprime attribute depends on the key through another nonprime attribute: key → X → A, with X and A both nonprime.

In COURSE, the key CID determines InsID, and InsID determines InsName — so InsName depends on the key only by way of InsID.

Inside COURSE(CID, CTitle, InsID, InsName):

CID → InsID InsID → InsName (transitive)

CID → InsID → InsName. InsName is one hop too far from the key.

Toward 3NF · the rule

3NF — no transitive dependency

A relation is in 3NF when it is in 2NF and no nonprime attribute transitively depends on a candidate key — every nonprime attribute depends on the key directly.

COURSE fails on InsName. The other three relations already pass.

How to fix it

Move the transitively-dependent attribute, together with the nonprime that determines it, into its own relation — keyed by that determinant. Leave the determinant behind as a foreign key.

Toward 3NF · the result

Decomposing to 3NF

Split InsName out of COURSE, keyed by InsID:

STUDENT(SID, SName)
COURSE(CID, CTitle, InsID)
INSTRUCTOR(InsID, InsName)
ENROLLMENT(SID, CID, Grade)

All four in 3NF

Every nonprime attribute now depends on its relation's key, wholly and directly. The anomalies from the wide table are gone — each fact lives in exactly one place, joined back by foreign keys.

Stated precisely

The general definition of 3NF

The partial/transitive phrasing is intuitive; here is the crisp test used in practice:

3NF (general form)

For every nontrivial FD X → A, either X is a superkey, or A is a prime attribute.

Check it FD by FD — and each check is a closure computation from last lecture.

The "or A is prime" escape

That second clause is what makes 3NF a little lenient: it tolerates a determinant that isn't a superkey, as long as what it determines is part of a key. BCNF removes that leniency — next lecture.

Reference

Normal forms at a glance

1NFAll attribute values are atomic — no repeating groups or nested relations.
2NF1NF, and no nonprime attribute is partially dependent on a candidate key.
3NF2NF, and no nonprime attribute is transitively dependent on a key — every nontrivial FD's LHS is a superkey or its RHS is prime.
BCNFEvery nontrivial FD's LHS is a superkey — no exceptions. Next lecture.

Each form implies the one above it. Most schemas target 3NF or BCNF.

A caveat to hold

Splitting a relation isn't free

A decomposition must earn two properties, or it does more harm than the anomalies it removes:

  • Lossless join — rejoining the pieces gives back exactly the original, no spurious rows.
  • Dependency preservation — every FD can still be checked without a join.

Good news for 3NF

A relation can always be decomposed into 3NF relations that are both lossless and dependency-preserving. BCNF can't always promise both at once — a tension we'll unpack in Normalization IV.

Judgment

Pitfalls & tips

  • Partial dependencies need a composite key. With a single-attribute key, 1NF already gives you 2NF — don't hunt for partials that can't exist.
  • Identify the candidate keys first. "Prime" and "nonprime" — and therefore every 2NF/3NF test — depend on knowing them.
  • Transitive means nonprime-to-nonprime. A dependency between two prime attributes isn't a 3NF problem.
  • Keep the join key. When you split off a relation, leave its determinant behind as a foreign key, or you can't rejoin.
  • Normalize for a reason. Each step trades a join for fewer anomalies; know which you're buying.
