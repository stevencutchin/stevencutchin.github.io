Motivation

Why model before tables?

A schema you type straight into SQL bakes in decisions you haven't examined yet. The ER model is a thinking tool that comes first.

  • It captures the mini-world — the slice of reality the database is about — in a form you can discuss with non-programmers.
  • It is DBMS-independent: no tables, types, or vendor syntax, just the concepts and how they connect.
  • It is a diagram, so mistakes are cheap to spot and fix now, versus after data is loaded.

The pipeline

Requirements → ER diagram (this unit) → relational schema (Unit 2, by a mechanical mapping) → SQL tables (Unit 4). Get the diagram right and the tables follow.

Building block 1

Entities: types and sets

An entity is a thing in the mini-world we want to store data about — a specific student, a specific course.

An entity type is the template: the name and the list of attributes every entity of that kind has. In Chen notation it is a rectangle.

An entity set is the collection of actual entities of that type at a moment in time — the rows below.

Type vs. set

STUDENT (the rectangle) is the type. The three students in the table are the set. The type is the design; the set is the data.

Building block 2

Attributes

An attribute is a property that describes an entity. Every entity of the type has the same attributes, each drawn from a set of allowed values called its domain.

In Chen notation an attribute is an oval joined by a line to its entity rectangle.

Attributes come in a few flavours — the next four slides work through each pair of choices. They matter because each one maps to the relational model differently later.

Attribute: an oval attached to its entity.

Attribute flavours · 1 of 4

Simple vs. composite

A simple (atomic) attribute holds one indivisible value — GPA, Major.

A composite attribute is built from smaller attributes. Name divides into First, Middle, and Last. You can refer to the whole thing or to any part.

Draw a composite by hanging its component ovals off the parent oval.

Design signal

Model something as composite only if you sometimes need the parts separately. If you always use the whole value, keep it simple.

Composite: parent oval with component ovals.

Attribute flavours · 2 of 4

Single- vs. multivalued

Most attributes are single-valued: one student has one birth date.

A multivalued attribute can hold a set of values for a single entity — a student may list several phone numbers. Chen notation marks it with a double oval.

Foreshadowing

Multivalued attributes don't fit directly in a table; in Unit 2 they become their own row set. Often that's a hint the value should be a separate entity.

Multivalued: a double oval.

Attribute flavours · 3 of 4

Stored vs. derived

A stored attribute is kept as-is — BirthDate.

A derived attribute is computed from other data rather than stored — Age follows from BirthDate and today's date. Chen notation uses a dashed oval.

Deriving avoids storing a value that would otherwise go stale or fall out of sync with what it depends on.

Derived: a dashed oval (Age from BirthDate).

Attribute flavours · 4 of 4

When a value is missing: NULL

Sometimes an attribute has no value for a particular entity. That absence is called NULL, and it can mean different things.

  • Not applicable — the attribute doesn't apply here. A student with no middle name has no MiddleName value.
  • Unknown — a value exists but we don't have it, or we're unsure whether one exists.

Why it matters

NULL is not zero and not the empty string. It behaves unusually in comparisons and aggregates — a recurring theme once we reach SQL in Unit 4. Flag now which attributes may be NULL.

Building block 3

Keys: telling entities apart

If two students shared every attribute value, we couldn't tell them apart. A key is an attribute (or a set of them) whose value is unique across the whole entity set — a uniqueness constraint.

Chen notation marks a key by underlining its name.

StudentID is a natural key here: the registrar guarantees no two students share one.

Keys, continued

Candidate keys and the primary key

An entity type can have more than one key. Each minimal uniquely-identifying attribute set is a candidate key — for a student, both StudentID and (say) their university email might qualify.

The designer picks one candidate to be the primary key, the official identifier; that's the one we underline.

A key can span several attributes together — a composite key — when no single attribute is unique on its own.

Choosing a primary key

  • Unique & never NULL — it must identify every entity.
  • Stable — values shouldn't change over an entity's life.
  • Minimal & simple — prefer few attributes and simple types.

"Minimal" precisely

No attribute can be dropped from a key and still keep it unique. {StudentID, Name} is a superkey but not a candidate key — StudentID alone already suffices.

Judgement

Design pitfalls & tips

  • Attribute or entity? If a "value" has its own attributes or needs to be shared, it wants to be an entity, not an attribute. Department as a bare text attribute vs. a DEPARTMENT entity is the classic call — we settle it in ER II.
  • Don't over-decompose. Composite and multivalued attributes are right sometimes, but reflexively splitting everything clutters the model. Split only where the parts do real work.
  • Name for the mini-world, not the code. BirthDate, not bd_field2. The ER diagram is a shared language with domain experts.
  • Pick the key deliberately. Reach for a stable identifier; be wary of keys built from data that can change, like a phone number.
