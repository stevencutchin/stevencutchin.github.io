The mechanism

Locking, in one idea

A lock is a right to access a data item. A transaction must acquire the appropriate lock before touching an item and release it afterward; a conflicting request must wait.

Locks serialize access to each item. With the right rule about when to acquire and release them, they force the whole schedule to be serializable.

The operations

lock_S(X) — lock X for reading; lock_X(X) — lock X for writing; unlock(X) — release. The lock manager grants or blocks each request.

Two lock modes

Shared & exclusive locks

  • Shared (S) — a read lock. Many transactions can hold an S lock on the same item at once; reads don't interfere.
  • Exclusive (X) — a write lock. Only one transaction can hold it, and no S locks may coexist with it.

A transaction upgrades S→X to write an item it was reading, and may downgrade X→S — carefully, so as not to break the two-phase rule.

Why two modes

Concurrent reads are safe and common, so a single exclusive lock would needlessly serialize them. Sharing read access is a big concurrency win.

The gap

Locks alone don't guarantee serializability

Suppose each transaction locks an item, uses it, and releases it immediately — then locks the next. Every access is protected, yet the schedule can still be non-serializable.

Releasing a lock too early lets another transaction slip in and create a conflict cycle. Correctness needs a rule about when locks may be released — not just that they're held during use.

The missing constraint

Once a transaction starts releasing locks, it must be done acquiring them. Enforce that and cycles become impossible. That rule is two-phase locking.

The protocol

Two-phase locking (2PL)

Every transaction splits its locking into two phases:

  • Growing phase — it may acquire locks, but release none.
  • Shrinking phase — once it releases its first lock, it may release more but acquire no new locks.

The switch-over — the moment it holds its maximum set of locks — is the lock point.

The guarantee

Any schedule of transactions that all obey 2PL is conflict-serializable. Order the transactions by their lock points and you get an equivalent serial order.

The intuition

Why 2PL forces an acyclic graph

Because no transaction acquires a lock after releasing one, if Ti's operation conflicts with Tj's, Ti's lock point must come before Tj's. All conflicts therefore point the same way, ordered by lock point.

A consistent ordering of all conflicts is exactly an acyclic precedence graph — the serializability condition from last lecture.

The price

2PL guarantees serializability but not freedom from deadlock: two transactions can each hold a lock the other is waiting for. That's the rest of the lecture.

Trading concurrency for safety

Variants of 2PL

Basic 2PLThe rule as stated. Serializable, but allows deadlock and cascading aborts.
Conservative 2PLAcquire all locks before starting. Deadlock-free — but you must predeclare, and concurrency drops.
Strict 2PLHold all exclusive locks until commit/abort. Cascadeless and strict — the common real-world choice.
Rigorous 2PLHold all locks (S and X) until commit. Simplest to reason about; even less concurrency.

What systems actually use

Most databases run strict 2PL: it gives serializable, cascadeless, recoverable schedules, and pairs cleanly with the recovery manager next lecture.

2PL's side effect

The deadlock 2PL creates

Two transactions can wait on each other forever:

T1T2
lock-X(A)
lock-X(B)
lock-X(B) …wait
lock-X(A) …wait

Stuck

T1 holds A and wants B; T2 holds B and wants A. Neither can proceed, neither will release. This deadlock is the price of letting transactions grab locks as they go.

Finding it

Detection: the wait-for graph

Build a wait-for graph: a node per transaction, an edge Ti → Tj when Ti is waiting for a lock Tj holds.

A cycle means deadlock. When one appears, the system picks a victim to abort and roll back, freeing its locks so the others proceed.

Cycle = deadlock. Abort a victim to break it.

Avoiding it

Prevention & timeouts

Instead of detecting cycles, prevent them. Timestamp-based schemes decide who waits and who dies by transaction age:

  • Wait-die — an older transaction waits for a younger; a younger one requesting an older's lock aborts (dies).
  • Wound-wait — an older transaction forces a younger to abort (wounds it); a younger one waits.

Both make waiting one-directional, so no cycle can form.

Simpler still: timeouts

Many systems just abort a transaction that waits too long. Crude, but cheap and cycle-proof. Conservative 2PL (all locks up front) avoids deadlock outright.

Practical concerns

Lock granularity & starvation

Granularity is what a lock covers — a row, a page, or a whole table. Fine locks maximize concurrency but multiply overhead; coarse locks are cheap but serialize more.

Intention locks on parent nodes let the system mix granularities safely — signalling "a descendant is locked" without scanning.

Starvation

A transaction can wait forever if it's always chosen as the deadlock victim, or if writers keep losing to a stream of readers. Fair scheduling (e.g. first-come-first-served on the lock queue) prevents it.

Judgment

Pitfalls & tips

  • Holding locks during use isn't enough. Serializability needs the two-phase rule: no acquire after any release.
  • 2PL guarantees serializable, not deadlock-free. You still need detection or prevention.
  • Strict 2PL is the default. Holding X locks to commit buys cascadeless recovery for a modest concurrency cost.
  • A cycle is the signal. Precedence-graph cycle = not serializable; wait-for-graph cycle = deadlock.
  • Granularity is a tuning knob. Row locks for concurrency, coarser locks to cut overhead — and watch for starvation.
