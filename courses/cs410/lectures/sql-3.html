Summarizing · 1

Aggregate functions

An aggregate collapses a set of values into one: COUNT, SUM, AVG, MIN, MAX. With no GROUP BY, the whole table is one group.

  • COUNT(*) counts rows; COUNT(col) counts non-NULL values.
  • COUNT(DISTINCT col) counts distinct values.
  • SUM/AVG/MIN/MAX also ignore NULLs.
SELECT COUNT(*)              AS n,
       AVG(GPA)             AS avg_gpa,
       MAX(GPA)             AS top_gpa,
       COUNT(DISTINCT Major) AS majors
FROM STUDENT;
-- n=4, avg_gpa=3.6, top_gpa=3.9, majors=3

One summary row over the whole table.

Summarizing · 2

GROUP BY — one row per group

GROUP BY partitions rows by the grouping columns and applies the aggregates within each group, returning one row per group.

"How many students, and what average GPA, in each major?"

SELECT Major, COUNT(*) AS n,
       AVG(GPA) AS avg_gpa
FROM   STUDENT
GROUP BY Major;
Result — one row per Major

Summarizing · 3

The rule that trips everyone

Every column in SELECT must be either a grouping column or inside an aggregate. Nothing else has a single value per group.

Asking for a bare Name alongside a per-major count is meaningless — which of the group's names would it be?

-- ERROR: Name is neither grouped
-- nor aggregated
SELECT Major, Name, COUNT(*)
FROM STUDENT
GROUP BY Major;

-- OK
SELECT Major, COUNT(*), MAX(GPA)
FROM STUDENT
GROUP BY Major;

Summarizing · 4

HAVING filters groups; WHERE filters rows

A condition on an aggregate can't live in WHERE — the groups don't exist yet. It goes in HAVING, applied after grouping.

  • WHERE — drops rows before grouping.
  • HAVING — drops groups after aggregating.

Use both together: WHERE to pre-filter, HAVING to test the summary.

-- majors with more than one student,
-- counting only GPAs at or above 2.0
SELECT Major, COUNT(*) AS n
FROM   STUDENT
WHERE  GPA >= 2.0
GROUP BY Major
HAVING COUNT(*) > 1;

WHERE first, then GROUP BY, then HAVING.

Reference

The full SELECT, in evaluation order

1FROM / JOINassemble the input rows
2WHEREfilter rows (σ)
3GROUP BYpartition into groups
4HAVINGfilter groups
5SELECTproject columns / aggregates (π)
6ORDER BYsort the final output

Why the order matters

SELECT is written first but evaluated fifth — which is why a column alias defined in SELECT can't be used in WHERE, and why an aggregate condition must wait for HAVING, not WHERE.

Abstraction · 1

Views — a query with a name

A view is a virtual table defined by a query. It stores no data of its own; querying it runs the underlying query.

Views earn their keep three ways:

  • Simplify — hide a complex join behind a friendly name.
  • Secure — expose only some columns or rows to a user.
  • Stabilize — a fixed interface even as base tables change.
CREATE VIEW cs_students AS
  SELECT StudentID, Name, GPA
  FROM   STUDENT
  WHERE  Major = 'CS';

-- use it like any table
SELECT * FROM cs_students
WHERE GPA > 3.8;

Abstraction · 2

When can you write through a view?

Reading a view is always fine. Writing through one is only well-defined when each changed row maps back to exactly one base-table row.

A view is generally updatable when it:

  • draws from a single base table,
  • includes that table's primary key, and
  • uses no DISTINCT, GROUP BY, aggregate, or join.

WITH CHECK OPTION

Add it so an INSERT or UPDATE through the view can't create a row that falls outside the view's own WHERE — no smuggling a non-CS student into cs_students.

Materialized views

A materialized view stores its result for speed and must be refreshed as base data changes — a query-performance tool, more in the storage unit.

Active rules · 1

Assertions — constraints across rows

A CHECK constrains one row. An assertion states a condition over the whole database that must always hold — spanning many rows or tables.

Write the rule as "there is no violation," using NOT EXISTS.

Rarely implemented

General assertions are expensive to check and most DBMSs don't support them. In practice the same rules are enforced with triggers — next slide.

-- no student may exceed 6 courses
CREATE ASSERTION max_load CHECK (
  NOT EXISTS (
    SELECT StudentID FROM ENROLLMENT
    GROUP BY StudentID
    HAVING COUNT(*) > 6));

Active rules · 2

Triggers — event, condition, action

A trigger is stored procedural code the DBMS runs automatically on a data event. Its three parts:

  • Event — BEFORE/AFTER an INSERT, UPDATE, or DELETE.
  • Condition — an optional WHEN test.
  • Action — the body; NEW and OLD name the row versions.
CREATE TRIGGER enforce_load
BEFORE INSERT ON ENROLLMENT
FOR EACH ROW
WHEN ((SELECT COUNT(*) FROM ENROLLMENT
       WHERE StudentID = NEW.StudentID) >= 6)
BEGIN
  -- reject the overload
  SIGNAL SQLSTATE '45000';
END;

Use triggers sparingly — logic hidden here is easy to forget.

Evolving the schema

ALTER TABLE — schema change after the fact

Schemas outlive their first draft. ALTER TABLE adds or drops columns and constraints without recreating the table.

  • ADD a column (existing rows get NULL or a DEFAULT).
  • ADD CONSTRAINT — the DBMS checks it against current data.
  • DROP a column or constraint.
ALTER TABLE STUDENT
  ADD Email VARCHAR(80);

ALTER TABLE STUDENT
  ADD CONSTRAINT chk_gpa
      CHECK (GPA <= 4.0);

ALTER TABLE STUDENT
  DROP COLUMN Email;

Judgment

Pitfalls & tips

  • Every SELECT column is grouped or aggregated. A bare column alongside an aggregate is the most common GROUP BY error.
  • Aggregate conditions go in HAVING, not WHERE. WHERE runs before groups exist.
  • COUNT(*) ≠ COUNT(col). The second skips NULLs — they can differ, and the difference is usually the point.
  • Not every view is updatable. Anything with a join, DISTINCT, or aggregate is read-only; add WITH CHECK OPTION to those that are writable.
  • Triggers hide behavior. They're powerful for integrity, but logic buried in a trigger surprises whoever debugs the app later.
