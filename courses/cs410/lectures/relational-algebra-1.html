Querying the relational model

Relational algebra I
Selecting, projecting, and set operations

We have relations. Now we need a precise way to ask questions of them.

Relational algebra is a small set of operations, each taking relations in and giving a relation out. Today: the unary operations and the set operations. It is the formal core that SQL sits on top of.

πFname, Salary( σDno=5(EMPLOYEE) )

A query is a function from relations to a relation — and the result is itself a relation, so operations chain.

Where we are

Recap & today's roadmap

Relational algebra is the procedural query language of that model: you specify a sequence of operations that computes the answer.

The two lectures

  1. RA I — today. SELECT, PROJECT, RENAME; UNION, INTERSECTION, DIFFERENCE, CARTESIAN PRODUCT.
  2. RA II. Joins, division, aggregation, outer joins, and query trees.

Why bother, when SQL is coming? Because SQL is evaluated as relational algebra. Reading a query plan means reading this.

Motivation

A language of operations on relations

Each operation takes one or two relations and returns a new relation. Nothing else is in play — no loops, no variables beyond the relations themselves.

  • Closure: the output of any operation is a relation, so it can feed the next operation. Whole queries are built by composition.
  • Set semantics: relations are sets of tuples, so results carry no duplicate rows and no inherent order.
  • Procedural: an expression is a recipe. You say how to compute the answer — unlike SQL, which leans declarative.

Two families today

Unary operations act on one relation (SELECT, PROJECT, RENAME). Set operations combine two (UNION, INTERSECTION, DIFFERENCE, CARTESIAN PRODUCT).

Unary · SELECT

SELECT (σ) — keep some rows

SELECT filters rows. It keeps the tuples that satisfy a condition and drops the rest; the columns are untouched.

σcondition(R)

The condition is a boolean test over attributes, built from comparisons (=, ≠, <, ≤, >, ≥) joined by AND, OR, NOT. The result has the same columns as R.

Read it aloud

σSalary>40000(EMPLOYEE) — "the employees earning more than 40,000."

σDno=5(EMPLOYEE)

Unary · PROJECT

PROJECT (π) — keep some columns

PROJECT filters columns. It keeps only the listed attributes and discards the others.

πattribute list(R)

Because the result is a set, any duplicate rows that appear after dropping columns are eliminated automatically. That difference from SQL (which keeps duplicates unless told otherwise) matters later.

Duplicate elimination

Projecting EMPLOYEE onto Dno collapses four rows into the two distinct department numbers.

Four employees, but only two distinct departments — the duplicate 5 and duplicate 4 are gone.

Putting them together

Composing operations

Because every result is a relation, you can nest operations directly:

πFname( σSalary>40000(EMPLOYEE) )

Read inside-out: select the well-paid employees first, then project their first names.

Or name the intermediate result with an assignment (←), which is often clearer for long queries:

HIGH ← σSalary>40000(EMPLOYEE)
RESULT ← πFname(HIGH)

Order matters for cost, not result

Selecting before projecting here gives the same answer either way, but doing the row filter first shrinks the data the next step touches — the seed of query optimization in Unit 7.

Watch what a step needs

You can't project a column away and then select on it. Each operation only sees the relation handed to it.

Unary · RENAME

RENAME (ρ) — change the names

RENAME gives a relation a new name, new attribute names, or both — without changing its tuples.

ρS(B1, B2, …)(R)

Why bother? Two situations force it:

  • Set operations need both relations to use the same attribute names.
  • Relating a relation to itself (an employee and their supervisor, both from EMPLOYEE) needs two differently-named copies.

Example

ρSUP(SupSsn, SupName)(EMPLOYEE) makes a second copy of EMPLOYEE whose columns won't clash with the original when we join the two in RA II.

Rename is pure bookkeeping — no rows added or removed — but without it several later operations can't even be written.

Set operations · setup

Set operations & union compatibility

Relations are sets of tuples, so the usual set operations apply — but with a type rule. UNION, INTERSECTION, and DIFFERENCE require the two relations to be union-compatible:

  • the same number of attributes (same degree), and
  • matching domains, attribute by attribute in order.

The result takes the attribute names of the first relation.

The odd one out

CARTESIAN PRODUCT (×) is the exception — it needs no compatibility, because it concatenates tuples rather than matching them up. It is the bridge to joins in RA II.

Example setup: let GRADS and UGRADS each be πStudentID, Name of two student relations — same two columns, same domains, so they're union-compatible.

Set operations · UNION

UNION (∪)

R ∪ S is every tuple that appears in R, in S, or in both. Duplicates collapse — a student in both inputs appears once.

Set operations · INTERSECTION

INTERSECTION (∩)

R ∩ S keeps only the tuples present in both relations.

GRADS ∩ UGRADS

Answering "who is in both groups?" Using the same two inputs, only the student who appears in each survives.

Definable from the others

R ∩ S = R − (R − S). Intersection is a convenience — but a very common one.

GRADS ∩ UGRADS
StudentIDName
S2Ben

Only S2 (Ben) is in both GRADS and UGRADS.

Set operations · DIFFERENCE

DIFFERENCE (−)

R − S keeps the tuples in R that are not in S.

GRADS − UGRADS

Order matters

Difference is not commutative: R − S and S − R generally differ. Say which side you mean.

It expresses "in the first but not the second" — the graduate students who are not also listed as undergraduates.

Set operations · PRODUCT

CARTESIAN PRODUCT (×)

R × S pairs every tuple of R with every tuple of S. The result's degree is the sum of the two degrees; its tuple count is the product.

On its own it is rarely meaningful — most of those pairings are nonsense. Its value is as a first step: follow it with a SELECT that keeps only the sensible pairings.

The pattern to remember

σcondition(R × S) — product then select — is exactly what a join packages into one operation. That's the opening of RA II.

2 employees × 2 departments = 4 combined rows, only some of which match:

Wrap-up

Recap & what's next

Today

  • SELECT (σ) keeps rows; PROJECT (π) keeps columns and drops duplicates.
  • RENAME (ρ) sets up set operations and self-references.
  • Set operations need union compatibility — except PRODUCT.
  • Closure lets everything compose into one expression.
