Relational Algebra I
Select, project, rename, and set operations

The tables exist. Now we ask the other half of the question: given relations, how do we compute a new one — the answer to a query?

Relational algebra is the procedural language underneath SQL. Master these operators and every SELECT you write later has a precise meaning you can trace by hand.

Foundations

A closed, procedural algebra

Every operator takes one or two relations and returns a relation — nothing else. That single property is what makes it powerful.

  • Closed. Because the output is a relation, an operator's result can be the input to the next. A query is a pipeline of operators.
  • Set-based. A relation is a set of tuples, so results carry no duplicates and no inherent order.
  • Procedural. Algebra says how to compute the answer, step by step. Its declarative twin — relational calculus (what, not how) — we'll meet at the end of the next lecture.

Why learn it at all?

SQL is translated into an algebra expression and optimized as one. When a query is slow or wrong, this is the level you reason at.

Unary operators · 1

SELECT (σ) — keep some rows

SELECT keeps the tuples that satisfy a condition and drops the rest. It is a horizontal cut — it never changes the columns.

σMajor = 'CS'(STUDENT)

The condition can combine comparisons with ∧ (and), ∨ (or), ¬ (not). The result has the same schema as STUDENT.

Not the SQL SELECT

Algebra's σ is the SQL WHERE. The word "SELECT" in SQL actually does the projection on the next slide — a lifelong source of confusion, so name it now.

Unary operators · 2

PROJECT (π) — keep some columns

PROJECT keeps the listed attributes and discards the others. It is a vertical cut.

πName, Major(STUDENT)

Because the result is a set, PROJECT removes duplicate rows that collapse together once the dropped columns are gone.

Duplicate elimination is automatic

πMajor(STUDENT) returns {CS, Math, Physics} — three rows, not four. SQL keeps duplicates unless you write DISTINCT; algebra never does.

Building a query

Composing: a query is a pipeline

Because the algebra is closed, feed one operator's output into the next. "The names of CS students" is a σ then a π:

πName( σMajor = 'CS'(STUDENT) )

Read it inside-out: first select the CS rows, then project their names. Order matters for cost, and sometimes for correctness — projecting away Major first would leave nothing to select on.

Two ways to write the same query

Nested, as above — or as a sequence with named intermediates:

CS ← σMajor='CS'(STUDENT)
RESULT ← πName(CS)

Next lecture: query trees

This pipeline drawn as a tree — leaves are relations, internal nodes are operators — is exactly how an optimizer sees a query.

Unary operators · 3

RENAME (ρ) — relabel without recomputing

RENAME changes a relation's name, its attribute names, or both, leaving every tuple untouched.

ρS(SID, Nm, Mj, G)(STUDENT)

It looks trivial, but two later operations require it:

  • A self-join — comparing a relation with itself — needs two different names for the same relation.
  • Set operations demand matching attribute names; rename lines them up.

Shorthand

Often written just to alias a relation: ρE1(EMPLOYEE) and ρE2(EMPLOYEE) give you two handles on EMPLOYEE so a supervisor query can pair a row with another row of the same table.

Set operators · setup

Set operations need compatible schemas

∪, ∩, and − treat relations as plain sets of tuples — but only when the two relations line up. They must be union-compatible:

  • the same number of attributes (same degree), and
  • matching domains, attribute by attribute, in order.

If the names differ but the domains match, ρ first.

Set operators · 1

Union (∪) and intersection (∩)

Union collects every tuple in either relation, with duplicates removed.

TOOK_CS310 ∪ TOOK_CS410

Intersection keeps only tuples present in both.

TOOK_CS310 ∩ TOOK_CS410

Both are commutative: order of the two operands doesn't matter.

Set operators · 2

Difference (−)

Difference keeps the tuples in the first relation that are not in the second.

TOOK_CS310 − TOOK_CS410

"Students who took CS310 but not CS410." Unlike ∪ and ∩, difference is not commutative: A − B ≠ B − A.

Why it matters later

Difference is how algebra expresses "for all" and "none of" queries — the seed of the DIVISION operator in the next lecture.

Set operators · 3

Cartesian product (×)

Cartesian product pairs every tuple of one relation with every tuple of the other. No condition, no matching.

STUDENT × ENROLLMENT

  • Degree adds: all columns of both.
  • Cardinality multiplies: |R| × |S| rows.

Rarely the goal itself

Most product rows are meaningless pairings. Follow × with a σ that keeps only the matching ones and you have a join — the heart of the next lecture.

4 × 4 = 16 rows; 4 + 3 = 7 columns.

Judgment

Pitfalls & tips

  • σ is WHERE; π is SQL's SELECT. The names cross over. Keep them straight and half the confusion disappears.
  • PROJECT silently removes duplicates. Expecting four rows and getting three usually means a projection collapsed them — by design.
  • ∪, ∩, − demand union compatibility. Mismatched degree or domains is not a runtime surprise — the expression is simply not well-formed.
  • Difference is directional. Always ask which relation is the "base" you're subtracting from.
  • Parenthesize. Operator precedence in algebra is not worth memorizing — make the pipeline explicit and it can't be misread.
