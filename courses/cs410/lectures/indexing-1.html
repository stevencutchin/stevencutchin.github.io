Fast lookups without reordering

Indexing I
Primary, clustering, secondary, and multilevel

A sorted file is fast on one field and slow to write. An index gives you the search speed without paying the ordering cost on the data itself — and you can have several.

Today: what an index is, the three kinds tied to file ordering, and how stacking indexes into levels makes lookups nearly constant.

The idea in one line

An index is a small, sorted, searchable side-file of (value → pointer) entries. Search the little file, then jump straight to the record.

The structure

What an index is

An index is an ordered file of two-field entries — (search-key value, pointer) — kept sorted by the value.

It's much smaller than the data file (two fields vs. whole records), so it holds more entries per block and is fast to search. Find the entry, follow its pointer to the record. Like the index at the back of a book.

Small sorted side-file; each pointer jumps to a record.

Two densities

Dense vs. sparse indexes

  • Dense — one index entry per record. Works on any file, ordered or not. Bigger index.
  • Sparse — one entry per block (a block anchor: the first record's key). Smaller index — but the data file must be ordered, so you can scan within a block after landing.

The link to come

Sparse needs order. So a primary or clustering index (file ordered on that field) can be sparse; a secondary index (file not ordered on it) must be dense.

Index type · 1

Primary index

A primary index is built on the ordering key field of a sorted data file. One entry per block — sparse — holding that block's anchor value and a pointer.

Search cost: binary-search the small index (log₂ bi blocks), then one data-block access — a big drop from searching the data file directly.

At most one

A file can be physically ordered on only one field, so it can have only one primary index. It's tied to the file's actual sort order.

Index type · 2

Clustering index

A clustering index is built on an ordering non-key field — a field the file is sorted on, but whose values repeat (many records per value).

One entry per distinct value, pointing to the first block that holds it. Records sharing a value are clustered together on disk, so a lookup reads a contiguous run.

Also at most one

Like a primary index, it depends on the file's physical order — so a file has one primary or one clustering index, not both.

Index type · 3

Secondary index

A secondary index is built on a field the file is not ordered on. Since there's no order to exploit, it must be dense — one entry per record.

  • On a key field: one pointer per entry, unique.
  • On a non-key field: multiple records per value — use a bucket of pointers, or repeated entries.

You can have many

Secondary indexes don't depend on file order, so build as many as you like — one per field you frequently search. This is how a table supports fast lookups on several columns at once.

Indexing the index

Multilevel indexes

An index is itself an ordered file — so build a (sparse) index on it. Repeat until the top level fits in a single block.

Each level shrinks the search by the fan-out (entries per block). So the number of block accesses is about logfan-out(entries) — only a handful of levels even for enormous files.

Straight to B-trees

Multilevel indexes are static — inserts and deletes disrupt them. The B+-tree is the dynamic, self-balancing version, and it's the whole of the next lecture.

Nothing is free

Indexes speed reads, tax writes

An index dramatically cuts read cost on its field — but every index must be updated on every insert, delete, and change to the indexed column, and it consumes disk space.

A write-heavy table with ten indexes pays ten extra updates per row. Indexes are a read-optimization you buy with write cost and storage.

The balance

Index the columns you search often; leave the rest alone. Over-indexing silently slows every write and inflates the database — a common, invisible performance drag.

Physical database design

Choosing what to index

Index selection is driven by the workload — the queries that actually run. Good candidates:

  • columns in frequent WHERE filters;
  • join columns (foreign keys especially);
  • columns in ORDER BY / GROUP BY;
  • high-selectivity columns (many distinct values).

Poor candidates

Low-selectivity columns (a boolean, a two-value status) — an index that still matches half the table barely beats a scan. And rarely-queried columns just add write cost.

A bonus win

Covering indexes & index-only scans

If an index's entries contain every column a query needs, the DBMS can answer from the index alone — never touching the data file. That's an index-only scan over a covering index.

A multi-column index on (Major, Name) can answer "names of CS students" without a single data-block read.

Why it's fast

The index is small and often cached; skipping the jump to the data file removes the most expensive step. Widening an index to cover a hot query is a classic tuning move.

Judgment

Pitfalls & tips

  • Sparse needs order. Only a primary or clustering index can be sparse; a secondary index must be dense.
  • One physical order → one primary/clustering. But secondary indexes are unlimited — that's how you cover several search fields.
  • Indexes tax every write. Each insert/delete/update maintains every affected index. Don't index columns you rarely query.
  • Low selectivity, low benefit. An index on a two-value column seldom beats a scan.
  • Multilevel is static. Its update problems are exactly what the B+-tree fixes next lecture.
