Stricter forms, cleaner dependency sets

Normalization III
BCNF and minimal cover

3NF left one loophole open. BCNF closes it — but at a price. And to reason about a schema's dependencies cleanly, we first boil them down to a minimal cover.

Two tools today: the strictest common normal form, and the canonical form of an FD set that every decomposition algorithm starts from.

The tension to watch

BCNF removes more redundancy than 3NF, yet a BCNF decomposition can lose the ability to check a dependency without a join. Which to accept is a real design decision.

Motivation

The loophole 3NF leaves open

3NF's "or the RHS is prime" clause is deliberately lenient. It lets a determinant that isn't a superkey stand, so long as what it determines happens to be part of a key.

That loophole permits some redundancy to survive — most visibly when a relation has overlapping candidate keys.

The fix, previewed

BCNF simply deletes the loophole: every determinant must be a superkey. Cleaner rule, and less redundancy — but as we'll see, not always reachable while preserving all dependencies.

The definition

Boyce–Codd Normal Form

BCNF

A relation is in BCNF when, for every nontrivial FD X → A, the determinant X is a superkey.

That's the whole rule — no exceptions, no prime-attribute escape. Every arrow in the schema must originate from a superkey.

How to test it

For each FD X → A, compute X+. If X+ is not all attributes, X isn't a superkey — and that FD violates BCNF. Closure, yet again.

Side by side

3NF vs. BCNF

3NF — for every nontrivial X → A

  • X is a superkey, or
  • A is a prime attribute.

Tolerates a non-superkey determinant when the target is prime.

BCNF — for every nontrivial X → A

  • X is a superkey. Full stop.

Strictly stronger: every BCNF relation is 3NF, but not conversely.

When do they differ?

Only when a relation has a determinant that isn't a superkey but determines a prime attribute — which needs overlapping candidate keys. The next slide is the textbook case.

3NF but not BCNF

The classic TEACH example

TEACH(Student, Course, Instructor)

Student, Course → Instructor Instructor → Course

Business rules: a student takes a course from one instructor; each instructor teaches one course.

Keys & forms

Candidate keys: {Student, Course} and {Student, Instructor} — so all three attributes are prime.

  • 3NF ✓ — Instructor → Course passes because Course is prime.
  • BCNF ✗ — Instructor isn't a superkey, yet it determines Course.

The algorithm

Decomposing to BCNF

For a violating FD X → A, split R into two: one relation holding X+, and one holding R with the determined attributes removed (but X kept, so they still join).

On the violation Instructor → Course:

INSTRUCTS(Instructor, Course)
ENROLLED(Student, Instructor)

Lossless — guaranteed

The two share Instructor, which is a key of INSTRUCTS, so the join reconstructs TEACH exactly with no spurious rows. BCNF decomposition is always lossless.

The catch

What the BCNF split loses

The decomposition is lossless — but the FD Student, Course → Instructor now spans both relations. No single table holds all three attributes, so you can't enforce that rule without joining.

That's a loss of dependency preservation — and it's not a bug in the algorithm; it's provably unavoidable for some relations.

The theorem

Every relation has a lossless BCNF decomposition. But not every relation has one that is also dependency-preserving. TEACH is exactly such a relation.

The design decision

3NF or BCNF?

Stay at 3NF when…

  • you must enforce every FD locally, without joins;
  • the leftover redundancy is small and controlled;
  • the violating FD is rare in practice.

Go to BCNF when…

  • removing all redundancy matters more;
  • the lost FD can be enforced by the application or a trigger;
  • a dependency-preserving BCNF decomposition happens to exist.

The usual advice

Aim for BCNF; fall back to 3NF when dependency preservation is essential and BCNF can't give it. 3NF is the guaranteed floor — always achievable losslessly and dependency-preserving.

Cleaning up the FD set

Minimal cover — why bother?

A set of FDs usually contains redundancy: split-apart right sides, needless left-side attributes, whole FDs implied by the others.

A minimal cover is an equivalent FD set — same closure — stripped to a canonical, non-redundant form. The 3NF synthesis algorithm needs one as input.

Equivalent, remember

"Equivalent" means each set implies the other — checked with closures from Normalization I. A minimal cover throws away nothing you can't already derive.

What "minimal" means

Three conditions of a minimal cover

  1. Singleton right sides. Every FD has exactly one attribute on the right (use decomposition to split X → AB into X → A, X → B).
  2. No extraneous left-side attribute. No attribute can be dropped from any left side while keeping the same closure.
  3. No redundant FD. No whole FD can be removed while keeping the same closure.

Not unique

A set can have several minimal covers — the result depends on the order you test FDs in step 3. All are equivalent; any one is fine.

The procedure

Computing it, in order

Apply the three conditions as steps, in this order:

  1. Rewrite every FD with a single attribute on the right.
  2. For each FD, try to remove each left-side attribute; drop it if the FD still follows (test with a closure).
  3. For each FD in turn, try to remove it entirely; drop it if it still follows from the rest.

Order matters within a step

In steps 2 and 3, each removal changes what's left, so test against the current set as you go. Do the interactive on the next slide to see each removal.

Why we did this

Minimal cover → 3NF synthesis

The minimal cover isn't just tidy — it's the input to the 3NF synthesis algorithm, which builds a good schema rather than splitting a bad one:

  1. Compute a minimal cover of F.
  2. Make one relation per FD (or per common left side).
  3. Add a relation for a candidate key if none is covered.

The payoff

Synthesis from a minimal cover yields a schema that is 3NF, lossless, and dependency-preserving — all three at once. We'll do the full algorithm, and compare it to decomposition, next lecture.

Judgment

Pitfalls & tips

  • BCNF is one clause simpler than 3NF. Drop the "or RHS is prime" escape — every determinant must be a superkey, period.
  • Lossless is guaranteed; dependency-preserving is not. A BCNF split always rejoins correctly, but may strand an FD across relations.
  • 3NF is the safe floor. When BCNF can't preserve dependencies, 3NF always can — that's why it's the default target.
  • Do minimal-cover steps in order. Singleton RHS, then reduce LHS, then drop redundant FDs — and re-test against the current set.
  • Minimal covers aren't unique. Different orderings give different (equivalent) results; don't expect one canonical answer.
