The index databases actually use

Indexing II
B-trees and B+-trees

Multilevel indexes were fast but brittle — inserts and deletes wreck them. The B+-tree keeps the speed and stays balanced automatically, no matter what you throw at it.

Today: the B-tree idea, the B+-tree refinement that databases prefer, and how a search, an insert, and a split actually work.

The headline

A B+-tree indexes billions of records in three or four block accesses — and self-balances on every write. It's the default index in essentially every relational database.

Motivation

The trouble with a static index

A multilevel index is built once over a sorted file. Then reality intrudes:

  • an insert has nowhere to go in a full block → overflow chains that lengthen and slow lookups;
  • a delete leaves gaps → wasted space and skew;
  • rebuilding the whole index periodically is expensive.

What we want

A tree that reshapes itself on every insert and delete — staying balanced, staying full enough, keeping the height low — with no global rebuild. That's the B-tree family.

The structure

The B-tree idea

A B-tree is a balanced multi-way search tree built for disk. Its defining traits:

  • High fan-out — each node is a block holding many keys and pointers, so the tree is very shallow.
  • Always balanced — every leaf sits at the same depth.
  • Kept partly full — nodes stay at least half full, bounding height and wasted space.

Why "shallow" matters

Height is the number of block accesses per search. With a fan-out in the hundreds, a tree of height 3–4 already indexes hundreds of millions of keys.

Inside a node

B-tree node structure

A node of order p holds up to p−1 sorted keys and p child pointers. The keys separate the subtrees: everything left of a key is smaller, everything right is larger.

In a plain B-tree, a data pointer sits beside every key, in internal nodes as well as leaves — a key found high in the tree needs no descent to the leaf.

The downside for databases

Storing a data pointer in every internal node eats space that could hold more keys — lowering fan-out, raising height. The B+-tree fixes exactly this.

The database variant

The B+-tree

The B+-tree makes two changes:

  • Internal nodes hold only keys — pure routing, no data pointers.
  • All data pointers live in the leaves, and the leaves are linked in a sorted chain.

Keys route; data lives in the chained leaves.

The payoff

Why B+-trees win for databases

  • Higher fan-out. No data pointers in internal nodes → more keys per block → shallower tree → fewer disk accesses per search.
  • Great range scans. The linked leaf chain lets you find a start key, then read consecutive leaves — ordered traversal for free.
  • Uniform search cost. Every lookup ends at a leaf, so every search is the same length — the tree height.

The upshot

Equality lookups, range queries, and ordered scans all run well on one structure. That versatility is why the B+-tree is the default database index.

The read path

Searching a B+-tree

Start at the root. At each node, compare the target with the routing keys and follow the matching child pointer. Repeat down to a leaf, then read the data pointer.

The number of block accesses is the height of the tree, ≈ logfan-out(N) — three or four for hundreds of millions of keys.

Range on top of it

Descend to the start key's leaf, then walk the leaf chain rightward until you pass the end of the range — no re-descent needed for each row.

The write path

Insertion & node splitting

Find the target leaf and insert in order. If the leaf overflows, it splits into two, and a separator key is pushed up to the parent.

If the parent then overflows, it splits too — a split can cascade to the root, and a root split adds one level, keeping every leaf at the same depth.

Copy up, don't move up

In a B+-tree the separator is copied to the parent — the key value still lives in the leaf, because all data stays at the leaves. (In a plain B-tree it moves up.) The interactive shows exactly this.

The write path · 2

Deletion & underflow

Delete the key from its leaf. If the leaf drops below half full — an underflow — the tree rebalances:

  • Borrow a key from an adjacent sibling that has a spare, and fix the parent separator; or
  • Merge with a sibling, removing a separator from the parent — which may cascade upward and can shrink the height.

Symmetry

Insertion grows the tree by splitting; deletion shrinks it by merging. Both keep every node at least half full and every leaf at the same depth — the invariants that bound the height.

Sizing it for disk

Fan-out, height, and physical design

A node is a disk block, so fan-out ≈ block size ÷ entry size — often several hundred. That huge branching factor is why the height stays at 3–4 even for billions of keys.

Upper levels are small and stay cached, so a search often costs just one real disk read at the leaf.

Design choices

Which columns get a B+-tree, whether the primary index is clustering (leaves hold the rows) or not, and how wide to make a covering index — the physical-design decisions from last lecture, now on the structure that implements them.

Judgment

Pitfalls & tips

  • B+-tree, not B-tree, for databases. Keeping data out of internal nodes raises fan-out and enables leaf-chain range scans.
  • Height is the cost. Search, insert, and delete are all ≈ the tree height — which stays tiny thanks to fan-out.
  • A hash index can't do ranges. Reach for a B+-tree unless the workload is pure equality lookups.
  • Splits and merges are local. Writes touch a path from leaf to root at worst — never a global rebuild.
  • Fan-out follows block size. Bigger blocks → more keys per node → shallower tree; it's a physical-design lever.
