Welcome to CS 410/510

Introduction to database systems

You already know how to organise data in memory. This course is about what changes when the data is large, permanent, and shared — and about the software built to manage it.

Today: what this course is, how it runs, and the question underneath all of it — what a database management system actually is, and why we don't just use files.

Why this course exists

From data structures to databases

In CS 321 you built beautiful structures — in memory, for one program, for one run. Databases begin exactly where those three assumptions break.

It all fits in memory

Real data outgrows RAM. A database keeps it on disk and makes the cost of reading it the thing to optimise — Unit 7.

It lasts only while the program runs

Data must persist — outlive any program, and survive a crash mid-write. That's recovery — Unit 8.

One program owns it

Many users and programs hit the same data at once, and it must stay correct. That's concurrency and transactions — Unit 8.

Say it precisely

Three words, defined

A database is a structured, persistent collection of related data that models some slice of the real world — a mini-world — kept for a purpose.

A DBMS (database management system) is the general-purpose software for defining, building, querying, and protecting databases — PostgreSQL, Oracle, SQL Server.

Together, the database plus the DBMS plus the applications make up a database system.

What a database is not

Not just "a lot of data," and not a single spreadsheet. The defining features are structure, relationships, persistence, and being shared and managed by software.

Careful with words

People say "database" for the DBMS, and vice versa. In this course we'll keep them distinct — the data vs. the software that manages it.

The alternative, and why it hurts

Why not just use files?

Before databases, each program kept its own files in its own format. It works — until the data is shared.

  • Redundancy: the same student is stored in several files, wasting space and drifting out of sync.
  • Inconsistency: update one copy, forget another, and now the data contradicts itself.
  • Brittle programs: change a file's layout and every program that reads it breaks.
  • No sharing or safety: concurrent access, access control, and crash recovery are left to each programmer.

Redundancy is the root of the trouble.

What makes it different

The database approach: four traits

The DBMS approach replaces private files with one shared, self-managing store. Four characteristics set it apart.

  1. Self-describing. The database carries its own schema in a catalog, so the data explains itself.
  2. Program–data independence. Programs are insulated from how the data is stored, so storage can change without rewrites.
  3. Multiple views. Different users see different tailored slices of the same data.
  4. Shared, controlled access. Many users at once, kept correct by transactions and protected by access control.

The next two slides take these in pairs.

Traits 1 & 2

Self-describing, and insulated from storage

Self-describing

Alongside the data, the DBMS keeps a catalog of metadata — the definition of every table, field, type, and constraint. A tool can understand a database it has never seen by reading its catalog.

Program–data independence

Because programs go through the DBMS, not the raw files, the storage can change — add an index, reorganise a file — without touching the programs. We'll make this precise next class as the three-schema architecture.

Contrast with files

In file processing the structure is baked into each program's code. In a database it lives once, in the catalog — described, not hard-coded.

Traits 3 & 4

Many views, many users, kept correct

Multiple views

One database can present a different view to each audience — a registrar sees enrolments; a student sees only their own record — all derived from the same shared data.

Concurrency & transactions

Many users read and write at once. The DBMS wraps work in transactions that are all-or-nothing and isolated, so two people registering at the same moment can't corrupt the data.

The promise (ACID, in one line)

A transaction either fully happens or not at all, never leaves the data in a broken state, doesn't get tangled with others, and survives a crash once committed. The full story is Unit 8.

Who does what

Actors on the scene

A working database has several roles around it — you'll play most of them this term.

  • Database administrator (DBA): owns the system — access, performance, backups, availability.
  • Database designer: decides what to store and how it's structured — the ER and relational design.
  • Application programmer: builds the programs that read and write the database.
  • End user: queries and updates the data to get work done — from casual to sophisticated.

In this course

You'll be designer and programmer on the project, end user every time you write SQL, and you'll meet the DBA's concerns in the storage, indexing, and transactions units.

A balanced view

Worth it — and when it isn't

What a DBMS buys you

  • Controlled redundancy and enforced integrity.
  • Access control and security.
  • Efficient querying via indexes and a query optimiser.
  • Backup and recovery from failures.
  • Shared access with concurrency control.

When a DBMS is overkill

It isn't free — money, expertise, and overhead. For a small, single-user, rarely-changing dataset, or a simple embedded or hard real-time system, plain files can be the right call. Engineering is trade-offs, not reflexes.
