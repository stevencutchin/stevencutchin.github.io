Is this schema any good?

Normalization I
Functional dependencies, axioms, and closure

We can design, query, and program a database. This unit asks a different question: is the schema itself well-designed — and if not, how do we know, and how do we fix it?

The answer rests on functional dependencies. Today we define them and build the machinery — axioms and closure — to reason about them.

From art to theory

Good ER design gave us decent tables by judgment. Normalization replaces the judgment with a test: given the dependencies, is a relation in a good normal form, yes or no?

Motivation

One wide table, lots of repetition

Suppose we cram enrollment into a single relation:

CLASS(StudentID, CourseID, StudentName, CourseTitle, Grade)

The student's name repeats on every course they take; a course's title repeats for every student in it. That redundancy is not just wasteful — it's a correctness hazard, as the next slide shows.

Why redundancy hurts

The three update anomalies

  • Insertion. Can't record a new course until some student enrolls — its title has nowhere to live without a key.
  • Deletion. Delete the last enrollment in a course and you lose the course's title entirely.
  • Modification. Rename a course and you must update it in every row — miss one and the data contradicts itself.

The common cause

All three come from storing a fact in many places. The cure is to split the relation so each fact lives once — but split it correctly. That "correctly" is what the theory pins down.

Before the formalism

Informal design guidelines

Four rules of thumb that the normal forms will later make precise:

  • Clear semantics — each relation is about one thing; don't mix entities in a table.
  • No redundancy — avoid designs that cause update anomalies.
  • Few NULLs — attributes that apply to a minority of rows belong elsewhere.
  • No spurious tuples — a decomposition must join back to exactly the original, no bogus rows.

Guidelines vs. guarantees

These are judgment calls. The rest of the unit turns the first two into a decidable test on functional dependencies, and the last into the lossless-join property.

The core concept

Functional dependencies

A functional dependency X → Y means: any two tuples that agree on X must agree on Y. X determines Y.

It is a constraint from the meaning of the data, true of every legal instance — not something you read off one table by luck.

Instances can only disprove

A table can show an FD is violated, but no table can prove one holds — that comes from the semantics of the mini-world.

On CLASS, the meaning gives us:

StudentID → StudentName CourseID → CourseTitle StudentID, CourseID → Grade

A grade depends on the pair; a name depends on the student alone.

Reading the dependencies

Where do FDs come from?

You get FDs from the rules of the domain, not from sample rows:

  • "Each student has one name" → StudentID → StudentName.
  • "Each course has one title" → CourseID → CourseTitle.
  • "One grade per student per course" → {StudentID, CourseID} → Grade.

The key of a well-formed relation determines every attribute — that's the FD we most want to be the only one.

Trivial vs. nontrivial

An FD X → Y is trivial when Y ⊆ X (it always holds, e.g. {A,B} → A). The interesting design questions are all about the nontrivial ones.

Keys, defined by FDs

Keys are just special FDs

The key concepts from Unit 2 get a precise FD definition:

  • Superkey X: X → all attributes — X determines the whole tuple.
  • Candidate key: a superkey with nothing removable — minimal.
  • Prime attribute: one that's part of some candidate key.

On CLASS

{StudentID, CourseID} determines every attribute, and neither column alone does — so it's the candidate key. StudentID and CourseID are prime; StudentName, CourseTitle, Grade are nonprime. Hold that distinction — 2NF and 3NF turn on it.

Inference · the core rules

Armstrong's axioms

Three rules let us derive every FD that a set logically implies. They are sound (derive only true FDs) and complete (derive all of them).

Reflexivity
Y ⊆ X ⟹ X → Y
a set determines its own subsets (trivial FDs).
Augmentation
X → Y ⟹ XZ → YZ
add the same attributes to both sides.
Transitivity
X → Y, Y → Z ⟹ X → Z
dependencies chain.

Why we need them

The FDs you're told are rarely all the FDs that hold. The axioms let you reach the rest — the full closure of the FD set, written F+.

Inference · shortcuts

Handy derived rules

These follow from the three axioms and save work in practice:

Union
X → Y, X → Z ⟹ X → YZ
combine right-hand sides.
Decomposition
X → YZ ⟹ X → Y, X → Z
split a right-hand side apart.
Pseudotransitivity
X → Y, WY → Z ⟹ WX → Z
chain with extra context W.

One-sided splitting only

Decomposition splits the right side. You may not split the left: X → Z does not let you conclude that a part of X determines Z. A very common mistake.

The workhorse computation

Attribute closure X+

The closure X+ is the set of all attributes that X functionally determines under a set of FDs. The algorithm is a fixpoint:

  1. Start with X+ = X.
  2. For any FD V → W with V ⊆ X+, add W to X+.
  3. Repeat until nothing new is added.

Why it's central

Nearly every normalization test reduces to a closure: does X → Y hold? ⟺ Y ⊆ X+. Is X a superkey? ⟺ X+ is everything. We use it constantly for the rest of the unit.

Check yourself · interactive

Compute {A}+ step by step

Given F = { A → B,  A → D,  B → C,  CD → E }, grow the closure of {A} one FD at a time.

Start: the closure is just {A} itself. Now look for any FD whose left side is already inside the closure.

{A}+ = A B C D E

Filled pills are in the closure so far. At the last step it's all five attributes — so {A} is a superkey.

What closure buys you

Three things closure decides

  • FD membership. Does X → Y follow from F? Compute X+ and check Y ⊆ X+ — no need to build all of F+.
  • Superkey test. X is a superkey iff X+ = all attributes.
  • Finding candidate keys. Shrink a superkey attribute by attribute; if the closure still covers everything, the removed attribute was redundant.

Equivalent FD sets

Two FD sets F and G are equivalent when each covers the other — every FD in F follows from G and vice versa (check with closures). That's the idea behind the minimal cover we'll compute two lectures from now.

Setting up the normal forms

Prime vs. nonprime attributes

Once you know the candidate keys, split the attributes:

  • Prime — belongs to at least one candidate key.
  • Nonprime — belongs to none.

The normal forms are stated in exactly these terms: 2NF and 3NF are about how nonprime attributes depend on the keys.

Preview of the tests

Roughly: 2NF forbids a nonprime attribute depending on part of a key; 3NF forbids it depending on another nonprime attribute. Both are closure checks — which is why we built closure first.

Judgment

Pitfalls & tips

  • FDs come from meaning, not data. Never infer an FD from a sample table — one coincidental instance proves nothing.
  • Don't split the left side. X → Z says nothing about a subset of X determining Z. Decomposition applies only to the right.
  • Compute a closure instead of guessing. "Is this a key?" and "does this FD hold?" are both just X+.
  • Trivial FDs are real but uninformative. Y ⊆ X always holds; they never drive a design decision.
  • Redundancy is the enemy, anomalies are the symptom. When you spot a repeated fact, expect all three anomalies.
