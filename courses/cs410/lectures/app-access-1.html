The core problem

The impedance mismatch

SQL is set-oriented: a query yields a whole relation at once. A host language like C or Java is record-at-a-time: it processes one value, one object, one loop iteration.

Their type systems differ too — SQL's DECIMAL, DATE, and NULL have no exact twin in the host language. Bridging both gaps is what this unit is about.

A set on one side, a loop on the other — a cursor connects them.

The landscape

Three ways to reach the database

Embedded SQLSQL written inside the host source and handled by a precompiler. Tight, checked at compile time.
Call-level APILibrary calls that send SQL as strings — JDBC, ODBC. No precompiler; portable across DBMSs.
DB programming languageLogic that lives in the database — stored procedures, SQL/PSM. Next lecture.

Same goal, different seam

All three send SQL and get results back. They differ in where the SQL is written, when it's checked, and how portable the result is. Today's slides work through the first two.

Approach 1 · 1

Embedded SQL & host variables

SQL statements sit in the host source, each marked EXEC SQL. A precompiler replaces them with library calls before the normal compiler runs.

Host variables pass data across the seam, written :var inside SQL. INTO reads a single-row result back into them.

EXEC SQL BEGIN DECLARE SECTION;
  char  sid[6], sname[51];
  float gpa;
EXEC SQL END DECLARE SECTION;

/* sid set by the program */
EXEC SQL SELECT Name, GPA
  INTO :sname, :gpa
  FROM STUDENT
  WHERE StudentID = :sid;

Host variables carry the colon prefix inside SQL.

Approach 1 · 2

Static vs. dynamic SQL

Static SQL is fixed at compile time — the precompiler sees the whole statement and can check and optimize it. Fast, but the query shape can't change at runtime.

Dynamic SQL is built as a string while the program runs, then prepared and executed. Flexible — a query builder, an ad-hoc reporting tool — at the cost of runtime parsing and no compile-time checking.

The trade, and the risk

Dynamic SQL is the only way to run a query whose text isn't known in advance — but building that text by pasting in user input is exactly where SQL injection enters. We'll disarm it next lecture with parameters.

Approach 1 · 3

Dynamic SQL: PREPARE and EXECUTE

Two steps: PREPARE parses and plans a statement held in a string; EXECUTE runs it, optionally with supplied values. A one-shot statement can use EXECUTE IMMEDIATE.

Preparing once and executing many times amortizes the parse cost when the same statement shape repeats.

char q[200] =
  "DELETE FROM ENROLLMENT "
  "WHERE Grade IS NULL";

EXEC SQL PREPARE stmt FROM :q;
EXEC SQL EXECUTE stmt;

/* one-shot form */
EXEC SQL EXECUTE IMMEDIATE :q;

Crossing the seam

Cursors — the result-set iterator

A single-row SELECT … INTO is fine, but most queries return many rows and a host variable holds one. A cursor is the iterator that bridges the mismatch.

Four verbs run its life:

  • DECLARE — bind a cursor to a query.
  • OPEN — run the query; sit before the first row.
  • FETCH — advance one row into host variables.
  • CLOSE — release it.
EXEC SQL DECLARE c CURSOR FOR
  SELECT StudentID, Name
  FROM STUDENT
  WHERE Major = :major;

EXEC SQL OPEN c;
/* ... fetch loop ... */
EXEC SQL CLOSE c;

Cursors, continued

The fetch loop & status codes

Loop, fetching until the cursor runs out. The DBMS reports status after each call: SQLCODE/SQLSTATE, where '02000' ("no data") ends the loop.

An updatable cursor can even change the current row — WHERE CURRENT OF c — for row-by-row edits.

while (1) {
  EXEC SQL FETCH c INTO :sid, :sname;
  if (SQLSTATE == "02000") break;
  process(sid, sname);
}

/* update through the cursor */
EXEC SQL UPDATE STUDENT SET Major=:m
  WHERE CURRENT OF c;

Approach 2 · 1

Call-level interfaces: ODBC & JDBC

Instead of a precompiler, a call-level interface is an ordinary library the program calls at runtime, passing SQL as strings.

  • ODBC — the language-neutral C standard.
  • JDBC — the Java analog, the model we'll use.

A driver for each DBMS implements the interface, so the same application code runs against different databases.

Embedded vs. CLI

Embedded SQL is checked early and can be faster; a CLI needs no precompiler and is portable. Modern applications lean on CLIs like JDBC.

Approach 2 · 2

JDBC in practice

Four objects do the work: a Connection, a Statement, and a ResultSet you iterate with next() — JDBC's cursor.

Close what you open

ResultSet, Statement, Connection each hold resources. Leaking them exhausts the connection pool — use try-with-resources.

Connection con = DriverManager
    .getConnection(url, user, pw);
Statement st = con.createStatement();
ResultSet rs = st.executeQuery(
  "SELECT Name, GPA FROM STUDENT "
+ "WHERE Major = 'CS'");

while (rs.next()) {
  String n = rs.getString("Name");
  double g = rs.getDouble("GPA");
}
rs.close(); st.close(); con.close();

Approach 2 · 3

Parameterized statements

A PreparedStatement holds a fixed SQL template with ? placeholders; you bind values into them separately.

Two payoffs: the statement is parsed once and reused, and — crucially — a bound value is never parsed as SQL. The value can't change the statement's structure.

The safety hook

That separation of code from data is the whole defense against SQL injection. We build the attack, and this fix, next lecture.

PreparedStatement ps = con.prepareStatement(
  "SELECT Name FROM STUDENT "
+ "WHERE Major = ?");

ps.setString(1, major);   // bind, don't concat
ResultSet rs = ps.executeQuery();

The value goes in the box; it never becomes part of the SQL.

Correctness across statements

Transactions from application code

By default each statement auto-commits. When several statements must succeed or fail together, turn autocommit off and bracket them with commit or rollback.

Enrolling a student and charging their account is one unit of work — both, or neither.

Preview

Why this actually keeps data correct under concurrency and crashes is Unit 8. Here it's just the application's control knob.

con.setAutoCommit(false);
try {
  st.executeUpdate(enrollSql);
  st.executeUpdate(chargeSql);
  con.commit();            // both succeed
} catch (SQLException e) {
  con.rollback();          // neither
}

Judgment

Pitfalls & tips

  • Close every cursor, ResultSet, and Connection. Leaks silently drain the connection pool until the app stalls.
  • Check the fetch status, not the row count. Loop until "no data" — assuming a count invites an off-by-one.
  • Prefer parameters over string-built SQL. Faster on reuse, and the only real defense against injection (next lecture).
  • Mind the type and NULL mapping. A SQL NULL fetched into a host variable needs an indicator (or wasNull() in JDBC).
  • Dynamic only when you must. If the statement shape is fixed, use static or a prepared statement — cheaper and checkable.
