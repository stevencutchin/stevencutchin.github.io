The key idea

A join is σ over ×

Cartesian product pairs every row with every row — mostly nonsense. A join is exactly the product followed by a select that keeps only the meaningful pairs:

STUDENT ⋈StudentID = StudentID ENROLLMENT
≡ σ…( STUDENT × ENROLLMENT )

So joins add no new power — they're a name for a pattern so common it deserves its own symbol and its own optimization.

Why give it a symbol

Writing × then σ every time is verbose, and a database never actually materializes the full product — it uses join algorithms that find matches directly. The ⋈ notation reflects how the query really runs.

Join flavors · 1

Theta join (⋈θ)

The most general join: keep paired rows that satisfy any condition θ, which may use =, ≠, <, ≤, >, ≥.

R ⋈θ S ≡ σθ(R × S)

The condition need not be equality. "Pair each student with every course whose minimum GPA they clear" is a theta join on ≥:

STUDENT ⋈GPA ≥ MinGPA COURSE

Columns are kept whole

A theta join keeps all columns of both relations, including any that the condition compared. The next two flavors are the special cases that tidy this up.

Join flavors · 2

Equijoin — θ is equality

An equijoin is a theta join whose condition is an equality — the everyday "match on the key" case.

ENROLLMENT ⋈CourseID = CourseID COURSE

Because both sides had a CourseID, the result carries it twice — one column from each input. That redundant column is exactly what the natural join removes.

Join flavors · 3

Natural join (⋈) — the workhorse

The natural join is an equijoin on all attributes the two relations share by name, with the duplicate column removed.

ENROLLMENT ⋈ COURSE

No condition is written — it's inferred from matching names. That's power and hazard both: rename first if the shared name isn't meant to match.

Depends on naming

If the columns were EnrCourse and CrsID, a natural join would find nothing in common and silently give you a product. Names carry the semantics here.

The "for all" operator

Division (÷)

Division answers "which entities are related to every value in a set?" Given TAKES(StudentID, CourseID) and a set of required courses, find students who took them all:

TAKES ÷ REQUIRED

The quotient keeps a StudentID only if pairing it with every CourseID in REQUIRED appears in TAKES.

Built from what you know

Division is expressible with ×, −, and π — it's the algebra's way of saying "for all," the dual of the "there exists" that a join gives you for free.

Beyond set theory

Aggregation & grouping (ℱ)

The operators so far never compute a total. Aggregation adds COUNT, SUM, AVG, MAX, MIN. Written with the grouping attributes on the left of ℱ and the functions on the right:

MajorℱAVG GPA(STUDENT)

One output row per group. With no grouping attribute, the whole relation is one group: ℱCOUNT StudentID(STUDENT) = 4.

NULLs are skipped

Aggregates ignore NULL inputs — an AVG over a column with missing values averages only the present ones. Watch this once we're in SQL.

Keeping the unmatched

Outer joins (⟕ ⟖ ⟗)

A plain (inner) join drops rows with no match — Omar vanishes because he has no enrollment. An outer join keeps them, padding the missing side with NULL.

  • Left ⟕ — keep all of the left relation.
  • Right ⟖ — keep all of the right.
  • Full ⟗ — keep all of both.

STUDENT ⟕ ENROLLMENT

How a query is really shaped

Query trees

Draw a composed expression as a tree: leaves are relations, internal nodes are operators, and data flows upward to the root, which is the answer.

"The names of students enrolled in a CS-major course" reads bottom-up: join, then select, then project.

Why it matters

The optimizer manipulates this tree — pushing a σ below a ⋈ to filter early, for instance. Same answer, very different cost. This is the bridge into query processing later in the course.

Read bottom-up: ⋈ → σ → π.

The declarative twin

Relational calculus — what, not how

Algebra is procedural: it lists the steps. Relational calculus instead describes the answer and leaves the steps to the system:

{ t.Name | STUDENT(t) ∧ t.GPA > 3.6 }

"The names of tuples t in STUDENT whose GPA exceeds 3.6" — no order of operations, just a condition.

Two forms

Tuple calculus ranges over rows; domain calculus ranges over column values. Both say what, not how.

Equally expressive

Algebra and (safe) calculus capture exactly the same queries — the standard of relational completeness. SQL is the practical language that blends both; it's where we go next.

Judgment

Pitfalls & tips

  • Natural join is name-driven. An unintended shared column name joins on too much; a mismatched name joins on nothing and gives a product. Check the common attributes before you write ⋈.
  • Inner joins silently drop rows. If a total looks low, an unmatched row was discarded — reach for an outer join when the unmatched ones matter.
  • Division is rare but the tell is "every/all." "Students who took all required courses" is ÷, not a join.
  • Aggregates and NULL. COUNT(*) counts rows; COUNT(attr) skips NULLs; AVG ignores them too. The difference bites in SQL.
  • Join order is a cost decision, not a correctness one. Push selections down the tree to filter before joining.
