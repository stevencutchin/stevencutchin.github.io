Vocabulary

Data models

A data model is a way of describing data: its structure, the operations on it, and the constraints it must obey. Models come at three levels of abstraction.

  • Conceptual (high-level): close to how people think — entities and relationships. The ER model lives here.
  • Representational (implementation): still logical but concrete — the relational model of tables.
  • Physical (low-level): how bytes sit on disk — records, files, indexes.

A distinction you'll use all term

Schema vs. instance

The schema is the design — the structure, defined once and changed rarely. It's the intension.

The instance (or database state) is the actual data at a moment in time — the extension. It changes with every insert, update, and delete.

You've seen this shape

Schema is to state what a CS 321 class is to its objects, or what an ER entity type is to its entity set. One template, many changing values.

The problem

Why layer it at all?

Three pressures pull in different directions, and a single flat description can't satisfy all three.

  • Different users need different views. A registrar and a student shouldn't see the same slice of the database.
  • Storage should be free to change. Adding an index or reorganising files shouldn't force every program to be rewritten.
  • The logical design should be stable. Applications want to depend on a steady picture of the data, not on today's storage tricks.

The idea

Describe the database at three levels and put a translation layer between them. Each level can change while the others hold still — that's the whole payoff.

The centrepiece

The three-schema architecture

Three descriptions of the same database, with mappings between them. Highlight each level to see what it is responsible for.

Three levels of description sit between a user and the stored bytes. The mappings between them are what make change safe — highlight a level to focus on it.

Level 1 of 3 · bottom

Internal level: how it's stored

The internal schema describes the physical storage: how records are laid out in files, and the access paths — indexes — that make lookups fast.

This is the CS 321 material doing real work: hash files, B+-trees, and the cost of a disk read. We return to it in depth in Unit 7.

Key point

It's the only level that knows about bytes, blocks, and indexes. Everything above is storage-agnostic.

Indexes are access paths into the stored files.

Level 2 of 3 · middle

Conceptual level: the whole picture

The conceptual schema is one logical description of the entire database for the whole community of users — every entity, relationship, and constraint — and nothing about physical storage.

This is exactly where the ER diagram you'll build next week lives, and later its relational translation. Design happens here.

The pivot

Hiding storage below and views above, the conceptual schema is the stable middle everything else is defined against.

The conceptual schema — your ER model, storage-free.

Level 3 of 3 · top

External level: tailored views

Each external schema (a view) shows one user group just the part they need, derived from the conceptual schema and hiding the rest.

A registrar sees enrolments and grades; a student sees only their own record. Same database underneath, different windows onto it.

Looking ahead

In SQL these become views (Unit 4) — named queries that behave like tables tailored to each audience.

Many views, one underlying schema.

The connective tissue

The mappings do the work

The three levels are joined by two mappings the DBMS maintains:

  • External / conceptual: turns a request against a view into one against the whole schema.
  • Conceptual / internal: turns that into physical operations on files and indexes.

A query travels down through the mappings; the answer travels back up.

The trade

Mappings cost translation effort at runtime. What you buy with it is the freedom to change one level without disturbing the next — data independence.

Two mappings, one on each seam.

The payoff

Data independence

The capacity to change a schema at one level without changing the level above it. The mapping absorbs the change.

Physical data independence

Change the internal schema — add a B+-tree index, reorganise files — and the conceptual schema and every application stay the same. Queries just run faster. This one is routine.

Logical data independence

Change the conceptual schema — add a table or an attribute — without disturbing existing views and the programs on them. Harder to achieve fully, but the same principle.

How to remember it

Name the level you changed: change the physical storage → physical independence; change the logical (conceptual) design → logical independence. The mapping on that seam hides the change from above.

Talking to the DBMS

Database languages

Classically the DBMS offers distinct languages, one per job:

  • DDL — define the (conceptual) schema.
  • SDL / VDL — describe storage, and views.
  • DML — query and modify the data.

In practice one language — SQL — rolls these together, which is why it's the whole of Unit 4.

Declarative — say what

High-level / declarative (set-at-a-time): you name what you want — "the CS majors" — and the DBMS works out how to get it. SQL works this way.

Procedural — say how

Low-level / procedural (record-at-a-time): you spell out how — fetch one record, follow a pointer, loop. That's the CS 321 style, and it's what declarative querying frees you from.

Where the DBMS runs

From centralised to three-tier

The same DBMS ideas have been packaged different ways as hardware changed:

  • Centralised: everything on one machine.
  • Client / server: a server owns the data; clients send requests.
  • Three-tier: a middle application layer sits between the client and the database — the shape behind most web apps.

Client · application server · database server.

The landscape

Classifying DBMSs

DBMSs are sorted along a few axes — worth a map even though this course stays with the relational mainstream.

  • By data model: relational (our focus), plus object, and the newer document, key–value, column, and graph families often grouped as "NoSQL."
  • By number of users: single-user vs. multi-user.
  • By distribution: centralised vs. distributed across sites.
  • By purpose: general-purpose vs. special-purpose; transactional vs. analytical workloads.

Our lane

A general-purpose, multi-user, relational DBMS — the model that has dominated for decades and the one the rest of the course develops.
