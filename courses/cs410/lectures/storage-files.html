Down to the disk

Storage & Files
Disk, records, and file organizations

Every clean design we've built still has to land on a physical device. Down here, one number dominates everything: how many blocks you read from disk.

Today: the memory hierarchy and the I/O cost model, how records pack into blocks, and the three ways to organize a file — each fast at something, slow at another.

Why physical, now?

The same query can run in one block read or a million, depending purely on how the file is laid out. Query speed is a storage decision as much as a logical one.

The setting

The memory hierarchy

Storage trades speed for capacity in layers: fast and tiny at the top, slow and vast at the bottom. Each step down is orders of magnitude slower.

Databases hold more data than fits in RAM, so the working set lives on disk (or SSD) and is pulled into memory as needed. Managing that movement is the storage layer's job.

Each layer down: much slower, much bigger.

The one number that matters

The disk-I/O cost model

Disk transfers happen in fixed-size blocks (pages) — the unit of I/O. Reading one byte or a whole block costs the same one block access.

Because a disk access — seek plus rotation — is ~100,000× slower than a memory access, we measure an algorithm's cost as the number of block accesses, and ignore CPU work by comparison.

The whole model

Cost ≈ blocks read + blocks written. Every file organization and index in this unit is judged by that count.

Symbols we'll use

B = block size, R = record size, r = number of records, b = number of blocks in the file. Costs come out in terms of b.

Packing the block

Records & blocking

Records are packed into blocks. The blocking factor is how many fit:

bfr = ⌊ B / R ⌋

So a file of r records needs b = ⌈ r / bfr ⌉ blocks — the number every cost is stated in.

  • Unspanned — a record never crosses a block boundary; simpler, wastes the leftover bytes.
  • Spanned — a record may straddle two blocks; packs tighter, needs a pointer to the continuation.
  • Fixed vs variable length — variable-length records (a VARCHAR, a repeating group) need length markers or delimiters.

Three layouts

Three ways to organize a file

No universal winner

Each organization is fast at one thing and slow at another. The choice follows the workload — which is exactly what the cost model lets us reason about.

Organization · 1

Heap (unordered) files

Records are simply appended at the end. No ordering, no structure.

  • Insert: read the last block, add the record, write it back — essentially constant cost.
  • Search: no help — scan on average b/2 blocks, b in the worst case.
  • Delete: find it (a scan), then mark it deleted; periodic reorganization reclaims the space.

When a heap is right

Bulk loading, small files, or workloads that read the whole file anyway. If most queries scan everything, ordering buys you nothing.

Organization · 2

Sorted (ordered) files

Records are kept in order of an ordering field. That order unlocks binary search.

  • Search on the ordering field: log₂ b block accesses — a huge win over a scan.
  • Range queries: find the start, then read consecutively.
  • Insert / delete: must preserve order — shifting records is costly, so real systems use an overflow area and reorganize periodically.

The catch

Binary search only helps for the one ordering field, and keeping the order makes writes expensive. That tension is what indexes (next lecture) resolve.

Organization · 3

Hashed files (static hashing)

A hash function maps a key to a bucket number, so a record's block is computed, not searched for.

  • Equality search: hash the key → go straight to the bucket. Roughly one block access.
  • Range search: no help — nearby keys scatter across buckets. Hashing has no order.

Two keys can hash to one bucket — a collision — handled with an overflow chain.

The static-hashing problem

A fixed number of buckets is fast until the file grows: buckets overflow, chains lengthen, and performance decays. The fix is to let the hash structure grow.

Hashing that grows

Extendible & linear hashing

Extendible hashing keeps a directory indexed by the first few bits of the hash. When a bucket overflows, only that bucket splits and, if needed, the directory doubles — no full reorganization.

Linear hashing splits buckets in a fixed round-robin order as the file grows, needing no directory at all.

Why it matters

Both keep equality search at roughly one or two block accesses even as the file grows and shrinks, avoiding static hashing's decay. This is how real hash-organized files stay fast.

Matching layout to workload

Which organization, when?

  • Full-scan or bulk-load workload → heap. Ordering earns nothing if you read everything.
  • Range queries or ordered output → sorted (or, better, a B+-tree index — next lecture).
  • Point lookups by key, no ranges → hashing. One access, if you never need order.

It's rarely either/or

A table has one physical organization but can carry several indexes on top, each a mini structure for a different access path. That's the whole of the next two lectures.

Reference

File organizations at a glance

Heap Equality: b/2 avg Range: b (scan) Insert: ~1
Sorted Equality: log₂ b Range: log₂ b + run Insert: costly
Hashed Equality: ~1 Range: no help Insert: ~1 (until overflow)

All costs on the organizing field, in block accesses. Off-field access is a full scan for every organization.

Judgment

Pitfalls & tips

  • Count block accesses, not instructions. Disk I/O dwarfs CPU; that's the only cost that matters here.
  • An organization helps one field only. Sorted or hashed on X does nothing for a query on Y — that needs an index.
  • Hashing has no order. Never reach for a hash file when you need ranges or sorted output.
  • Sorted files pay on every write. Great for read-mostly data; painful under heavy inserts unless you use overflow + reorganization.
  • Static hashing decays. As data grows, prefer extendible or linear hashing over a fixed bucket count.
