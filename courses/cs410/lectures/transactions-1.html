The unit of work

What a transaction is

A transaction is a logical unit of work — a sequence of reads and writes that must take effect all together or not at all.

The archetype is a bank transfer: debit one account, credit another. Half of that — money leaving one account but never arriving — must never be a state the database can be left in.

Both writes commit, or neither does.

Two threats

Two things transactions defend against

Concurrency

Many transactions run at once. Interleave their reads and writes carelessly and they corrupt each other's data — even though each is correct alone.

Failure

A crash, a power loss, an error mid-transaction can leave updates half-applied. Recovery must undo the partial work and leave a consistent state.

Isolation handles the first; atomicity and durability handle the second. Together they're ACID.

The four guarantees

ACID

AtomicityAll operations happen, or none do. A failed transaction is rolled back completely.
ConsistencyA transaction moves the database from one valid state to another, preserving all constraints.
IsolationConcurrent transactions don't see each other's partial work — the result is as if they ran one at a time.
DurabilityOnce committed, changes survive crashes — they're permanently recorded.

Who provides which

Isolation is the concurrency control's job (today and next lecture); atomicity and durability are the recovery manager's (lecture 3). Consistency emerges when the others hold.

The lifecycle

Transaction states

Operations are read_item, write_item, commit, abort. A transaction moves through states:

  • Active → executing operations.
  • Partially committed → last op done, not yet saved.
  • Committed → durably recorded.
  • Failed → aborted → rolled back.

What goes wrong

Concurrency anomalies

  • Lost update — two transactions read the same value and overwrite each other; one update vanishes.
  • Dirty read — a transaction reads another's uncommitted value, which then aborts.
  • Unrepeatable read / incorrect summary — a value changes under a transaction mid-computation, so its reads disagree.

The formal object

Schedules: serial and nonserial

A schedule is an ordering of the operations of several transactions that preserves each transaction's own order internally.

  • Serial — transactions run one entirely after another; always correct, but no concurrency.
  • Nonserial — operations interleave; concurrent, but possibly incorrect.

The goal: interleave for performance, without the errors.

Notation

We write operations as r1(X) (T1 reads X), w2(Y) (T2 writes Y), and read a schedule left to right as time.

The correctness standard

Serializability

A serial schedule is correct by definition. So we call a nonserial schedule serializable when its effect is equivalent to some serial schedule of the same transactions.

Serializability is the gold standard for concurrency: an interleaving is safe exactly when it's serializable. The rest of the lecture is how to test for it.

Which equivalence?

Conflict equivalence is the practical one: it's efficiently testable and slightly stricter than the more general (but harder) view equivalence.

The building block

When do two operations conflict?

Two operations conflict when all three hold:

  • they belong to different transactions,
  • they access the same data item, and
  • at least one is a write.

So the conflicting pairs are read–write, write–read, and write–write. Two reads never conflict.

Why it matters

Non-conflicting adjacent operations can be swapped without changing the result. Conflicting ones can't — their order is what determines correctness.

Testable equivalence

Conflict serializability

A schedule is conflict-serializable if it can be turned into a serial schedule by repeatedly swapping adjacent non-conflicting operations.

Since only conflicts fix the order, whether that's possible depends entirely on the pattern of conflicts between transactions — which we can capture in a graph.

The plan

Rather than trying swaps by hand, build a precedence graph of the conflicts and read the answer off its shape. Next slide.

The test

The precedence graph

Build a directed graph:

  • one node per transaction;
  • an edge Ti → Tj whenever a conflicting operation of Ti comes before one of Tj.

The theorem

A schedule is conflict-serializable if and only if its precedence graph is acyclic. A cycle means the transactions each must come before the other — impossible in any serial order.

Bonus

If the graph is acyclic, a topological sort of it gives an equivalent serial order — the exact sequence the schedule is equivalent to.

Beyond serializability

Recoverable, cascadeless, strict

Serializability isn't the only requirement — schedules must also survive aborts:

  • Recoverable — a transaction commits only after every transaction it read from has committed. Otherwise a commit can't be undone when the source aborts.
  • Cascadeless — read only committed data, so one abort never forces others to roll back.
  • Strict — don't read or overwrite uncommitted data at all; the simplest to recover.

Where this leads

Real systems want serializable and strict schedules. The locking protocol next lecture delivers both — without hand-checking every interleaving.

Judgment

Pitfalls & tips

  • Serial is safe; nonserial needs proof. Interleaving buys speed but requires a serializability check.
  • Only reads never conflict. Any pair touching the same item with a write is a conflict — and fixes the order.
  • Acyclic ⟺ conflict-serializable. The precedence graph turns a hand-swapping puzzle into a cycle check.
  • Serializable isn't enough. A schedule must also be recoverable — ideally strict — to survive aborts.
  • Conflict ⊂ view serializable. Conflict serializability is the practical, efficient test, slightly stricter than view.
