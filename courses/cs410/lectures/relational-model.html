Logical database design

The Relational Model
Relations, keys & integrity

We've been drawing pictures. Now we meet the formal model the whole rest of the course is built on.

One idea — data as relations, plain tables with a precise mathematical meaning — plus a handful of integrity rules the DBMS guarantees on every change. Everything after this (SQL, algebra, normalization, indexing) operates on relations.

Motivation

Why this model won

Before 1970, databases were navigational: to find data you followed pointers through a structure that mirrored physical storage. Change the storage, break every program.

Codd's relational model made a radical bet: describe data as relations — sets of rows — with a foundation in set theory and logic, and nothing about how it's stored.

  • Simple. One structure: the table. No pointers to chase.
  • Formal. A precise math meaning enables provably-correct query languages (algebra, SQL — coming up).

The winning property: data independence

Because the model says nothing about storage, the DBMS is free to change indexes, file layout, and hardware without touching a single query. That decoupling — logical design above, physical below — is exactly the three-schema idea from Unit 0, now paying off.

You state what you want, not how to fetch it. The system figures out how.

Building block 1

A relation, precisely

Informally a relation is a table. Formally it's a set of tuples over a fixed list of attributes.

Two levels, and the distinction matters all course long:

  • The relation schema — the name and attributes, STUDENT(StudentID, Name, Major). Fixed at design time.
  • The relation state (instance) — the actual set of rows right now. Changes with every insert and delete.

Same schema, endlessly many possible states.

Schema vs. state — the parallel

This is the entity type vs. entity set distinction from ER I, now in the relational world. The schema is the design; the state is the data.

STUDENT(StudentID, Name, Major) has degree 3. Whether it holds 0 rows or a million, it's the same relation schema.

Terms that map to the picture

The vocabulary

  • A tuple is a row — one entity's worth of values.
  • An attribute is a named column.
  • A domain is the set of allowed values for an attribute (e.g. GPA ∈ 0.0–4.0).
  • Degree = number of attributes (columns).
  • Cardinality = number of tuples (rows) in the current state.

Formal term on the left, the table word you already know on the right.

Building block 2

Domains & atomic values

Every attribute draws its values from a domain: a named set of allowed, same-type values — StudentID is a 5-character code, GPA is a number in [0, 4].

Relational domain values must be atomic: indivisible, with no internal structure the model looks inside. One cell, one value — no lists, no nested tables.

Why atomic matters

Atomic values are what make a table a well-behaved relation — this is the first normal form we'll formalize in normalization. A cell holding "Math, CS" already breaks the model.

Where the ER attribute flavours land

  • Composite (Name → First, Last): store the atomic parts as separate columns.
  • Multivalued (Phone): can't live in one cell — it becomes its own relation.

The atomicity rule is exactly why those ER shapes need special handling when we map to tables next session.

Building block 3 · it's a set

What makes it a relation

Because a relation is a mathematical set of tuples, four properties follow — each with a practical consequence.

  • Tuples are unordered. A set has no first or last row. "The row order" is not information; never rely on it.
  • No duplicate tuples. A set has no repeats, so every relation needs a key to keep rows distinct — which is the next topic.
  • Values are atomic. One indivisible value per cell (first normal form).
  • Attributes are named, values from a domain. Column order is irrelevant when you refer to columns by name.

And when a value is missing: NULL

A tuple may hold NULL for an attribute — value unknown, or not applicable. NULL is not 0 and not the empty string; it will behave unusually in SQL comparisons and aggregates later.

Keys · 1

Superkeys & candidate keys

Because rows must be distinct, we need attribute sets that guarantee uniqueness.

A superkey is any set of attributes whose values are unique across every tuple — no two rows agree on all of them. {StudentID} is one; so is {StudentID, Name}, and any other set containing StudentID.

A candidate key is a minimal superkey: remove any attribute and it stops being unique. {StudentID} is a candidate key; {StudentID, Name} is not — Name is redundant.

The chain

Every candidate key is a superkey; not every superkey is minimal. A relation can have several candidate keys — StudentID and, say, a unique university email.

"Minimal" ≠ "smallest"

Minimal means no attribute is removable. A candidate key may still span several attributes (a composite key) when no single one is unique.

Keys · 2

Primary key & entity integrity

From the candidate keys, the designer picks one primary key — the official identifier for the relation, underlined in a schema.

The primary key carries a built-in rule, entity integrity: no part of a primary key may be NULL.

Why the rule must hold

The primary key is how every tuple is identified and referenced. A NULL key value would mean "a row we can't identify" — it couldn't be told apart or pointed to. So the DBMS refuses it outright.

Choosing among candidates

  • Stable — its value shouldn't change over a row's life.
  • Simple & short — prefer one attribute, simple type.
  • Never NULL — guaranteed by entity integrity anyway.

This is the ER I key decision, now with a formal name and a constraint the system enforces.

Keys · 3 · the glue

Foreign keys & referential integrity

Relations are linked not by pointers but by values. A foreign key is an attribute in one relation whose value must match a primary-key value in another (or the same) relation.

Referential integrity: every foreign-key value must either equal an existing primary key in the referenced relation, or be NULL. No dangling references.

This is where relationships live

Every relationship you drew in ER becomes a foreign key (or a bridge relation). "ENROLLED_IN.StudentID → STUDENT" is the M:N link from the ER diagram, now enforced as a value-matching rule.

The FK value S1002 must name a real STUDENT.

The rules, together

The integrity constraints

A relational schema isn't just tables — it's tables plus the rules the DBMS promises to keep true after every change.

  • Domain constraint — each value comes from its attribute's domain (right type, allowed range).
  • Key constraint — no two tuples share the same value on a candidate key (uniqueness).
  • Entity integrity — no primary-key attribute is NULL.
  • Referential integrity — every foreign key matches an existing primary key, or is NULL.

Declared once, enforced always

You state these when you define the schema; from then on the DBMS rejects any insert, update, or delete that would break them. Correctness moves out of application code and into the database itself — a large part of why we use one.

Interactive · the rules in action

Which constraint does it break?

Working from STUDENT(StudentID, Name) and ENROLLED_IN(StudentID, CourseNo) with StudentID a foreign key into STUDENT — pick an operation and see what the DBMS does.

Key constraint. Rejected: two students would share a primary-key value, so the rows couldn't be told apart. The insert fails.

The point

Three of the four are outright rejections. The fourth — deleting a referenced row — has choices (block it, cascade the delete, or set the foreign key to NULL); we'll set that policy in SQL.

Judgement

Why this model is the hinge of the course

  • It's the target of design. Everything in Unit 1 exists to produce a good relational schema; everything after operates on one.
  • Keys are decisions, not formalities. A stable, minimal primary key and honest foreign keys prevent whole classes of bugs the application would otherwise have to police.
  • Constraints are correctness you get for free. Declared in the schema, enforced by the DBMS on every change — no application code required.
  • It's still logical, not physical. No indexes, no file layout, no types yet. That independence is the model's greatest strength; we add the physical layer much later.
