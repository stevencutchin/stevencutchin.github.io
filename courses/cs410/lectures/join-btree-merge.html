Query processing · what the engine actually does

A join is a walk
down two sorted lists

A join looks like set theory on the page and like magic in the engine. It is neither. At the bottom it is two cursors moving forward through two ordered sequences, comparing the key under each one.

The ordered sequences come from B+tree indexes — because the leaf level of a B+tree is a sorted linked list. Once you see that, the join algorithm is the merge step you already know from merge sort, with one extra rule for repeated keys. That extra rule is the whole of the interesting part.

The bold boxes are the one key the two sides agree on.

Motivation

Why this is worth an hour

You can write correct SQL without knowing any of this. You cannot read a query plan, choose an index, or explain a slow query without it.

  • Query plans stop being opaque. Index Nested Loop, Merge Join and Hash Join in an EXPLAIN output are three concrete strategies, and today you see two of them in full.
  • Index choice becomes a decision, not a habit. An index on a join column is not "make it faster" — it supplies sorted order, which is the input the merge strategy needs.
  • Join cost becomes estimable. HW3 asks you to estimate one. The estimate comes straight out of the picture on the next few slides.

The claim we are going to defend

A join of two indexed relations is list traversal plus reconciliation. Traversal: walk forward through each index's leaf level, which is already in key order. Reconciliation: at each position decide which side is behind and advance it, and when the two agree, emit the matches. No backtracking, no nested scanning, one pass over each input.

What we are not covering today

Hash join (no ordering, equality only) and external sort-merge for unindexed inputs. Both appear on the cost comparison at the end, and both come back in the optimization lecture.

The specification

What must come out

The definition says: form every pair of one row from each side, keep the pairs where the predicate holds.

ENROLLED_IN ⋈CourseID TEACHES ≡ σ[e.CourseID = t.CourseID]( ENROLLED_IN × TEACHES )

Six rows × four rows = 24 candidate pairs, of which 7 survive. That is the answer, and it is the only thing any algorithm is allowed to produce. Everything that follows is about not doing 24 comparisons.

The naive cost

Nested loops is |R| × |S| comparisons. On six and four rows that is free. On a million enrollments and ten thousand teaching assignments it is 1010 comparisons, and that is before any disk page is read twice.

The structure we are standing on

Internal nodes route. Leaves hold everything.

In a B+tree the internal nodes carry separator keys only — signposts that tell a descent which child to take. No data hangs off them.

Every actual key lives at the leaf level, in ascending order, each one paired with a pointer to its row (or, in a clustered primary index, with the row itself).

Because the fan-out of a node is large — typically 100 to 300 keys on a disk page — the tree is short. Millions of rows sit under three or four levels.

The property that matters today

Leaf nodes are chained left to right by next-leaf pointers. This is the "+" in B+tree, and it is exactly what a B-tree lacks.

The idea the whole lecture turns on

A B+tree is a sorted list
with a fast way in

Ignore the upper levels for a moment and look only at the leaves. What is left is a singly linked list of keys in ascending order.

What the upper levels buy you

One thing: an entry point. A descent of height h lands you at any key in the list in h page reads instead of scanning from the front. That is the only service the internal nodes provide to a join.

What the leaf chain buys you

Everything else: ordered forward traversal from wherever you landed, with no further descents and no sort. The data is already in join-key order, for free, permanently, maintained by every insert.

Both lists are sorted on the same attribute. That is the entire precondition for the algorithm we are about to run — and it is the precondition a B+tree hands you without being asked.

Two strategies are now available

  1. Probe repeatedly. Walk one list; for each entry, descend the other tree to look its key up. Uses the upper levels, ignores the leaf chain.
  2. Walk both. Descend each tree once to find the start, then advance through both leaf chains together. Uses the leaf chain, ignores the upper levels after the first descent.

These are index nested loop join and merge join. Next two slides take them one at a time.

Strategy 1 of 2 · random access

Probe once per outer row

Scan the outer relation in any order at all. For each row, take its join key and descend the inner tree to find the matching leaf entries. Emit a pair for each one found.

for each row e in ENROLLED_IN: leaf = descend( TEACHES_idx, e.CourseID ) // h page reads while leaf.key == e.CourseID: emit( e, leaf.row ) leaf = leaf.next

Four of our six enrollments find nothing and pay for the descent anyway. The two that match pay the descent plus the matches.

Where the cost sits

|R| descents of height h. The upper levels cache well, so the real bill is roughly one random leaf read per outer row, plus one row fetch per match if the index is not covering. Random reads are the expensive kind.

Strategy 2 of 2 · sequential traversal

Descend once. Then just walk.

Descend each tree one time to reach the start of its leaf chain. From then on, never touch the upper levels again. Keep one cursor in each chain and move them forward.

Both cursors only ever move forward, and between them they traverse each list exactly once. That is the whole control structure: two pointers, monotonically advancing.

Why it terminates so cheaply

Every step advances at least one cursor, and no cursor ever goes backward past a key it has finished with. So the total work is bounded by |R| + |S| — additive, not multiplicative. The six-and-four example costs ten steps, not twenty-four.

The heart of it

Three cases, and nothing else

At every step you compare the two keys under the cursors. There are exactly three possible answers, and each one dictates a move.

The entire decision procedure. Nothing is ever compared twice.
Comparison What it means Move
kL < kR The left key is behind. Everything further right is larger, so this key can never match. It is an orphan. Advance the left cursor. Emit nothing.
kL > kR The right key is behind, by the same argument, mirrored. Advance the right cursor. Emit nothing.
kL = kR A match. But possibly many of them — each side may hold a run of this key. Emit every pair from the left run × the right run, then advance both past their runs.

Why "reconciliation" is the right word

This is the same procedure a bookkeeper uses to reconcile two sorted ledgers: read down both columns together, tick off what agrees, and when one side is behind, advance it alone. Items present on only one side fall out — which is precisely what an inner join does to CS354, CS481 and CS471.

while L and R not exhausted: if L.key < R.key: advance L elif L.key > R.key: advance R else: lrun = all of L with this key rrun = all of R with this key emit lrun × rrun advance L, R past their runs

Count the work

Six left entries and four right entries were each visited once. Seven result rows came out. The naive nested-loop version would have performed 24 comparisons to produce the same seven rows.

The one genuine subtlety

Duplicates: where it stops being merge sort

In merge sort, equal keys are emitted one at a time and both cursors step forward. In a join, equal keys must produce a cross product of the two runs — and that needs the right cursor to go over the same ground repeatedly.

Engines implement this with mark and restore: when a match is found, mark the start of the right run; after each left row in the run is paired off, restore the right cursor to the mark and replay it.

The one place the cost is not additive

With runs of length m and n, that key alone produces m × n rows and costs that much work. Normally fine. On a low-cardinality join column — a status flag, a term code — the runs are enormous and merge join degrades toward the nested-loop cost it was supposed to avoid.

If one side is unique

Join on a primary key and the right run is always length one. No mark, no restore, no replay — a pure merge. This is why PK–FK joins are the cheap, common case.

A free consequence

The keys that never match

CS354 and CS481 exist only in ENROLLED_IN. CS471 exists only in TEACHES. In the inner join they are stepped over and forgotten — the "advance and emit nothing" branch.

But notice the algorithm knows about them. It sees exactly which keys fall out and on which side. That is the whole reason outer joins cost almost nothing extra here.

Same traversal, different thing done in the skip branch.

Work it through

LEFT OUTER adds CS354/S1002 and CS481/S1005, the two left keys with no partner — 7 + 2 = 9. RIGHT OUTER adds CS471/E40, the one unmatched right key — 7 + 1 = 8. FULL adds all three — 7 + 3 = 10.

Contrast with the probing strategy

Index nested loop gets LEFT OUTER just as cheaply — a failed probe is a NULL row. But it has no idea which inner rows went unvisited, so RIGHT and FULL OUTER need a second pass or a different algorithm. The merge sees both sides at once; that symmetry is worth something.

Three strategies, side by side

Strategy Needs Rough cost Access pattern Wins when
Nested loop nothing |R| × |S| repeated full scan one input is tiny, or no index exists and no sort is affordable
Index nested loop B+tree on S's join column |R| × (h + matches) random, one descent per outer row R is small or heavily filtered, and the index is selective
Merge join both inputs in join-key order |R| + |S| sequential, one pass each both sides already sorted — by index, or by an earlier operator
Hash join equality predicate, memory for the build side |R| + |S| sequential plus random probes in memory large unsorted inputs, equijoin, no useful index

The caveat that bites in practice

A secondary index gives you keys in order but not rows in order. Walking its leaves in key order means a random row fetch per entry, and the sequential advantage evaporates. Merge join is at its best over a clustered index, or over an index that already covers every column the query needs.

Wrap-up

Recap & what's next

Today

  • The leaf level of a B+tree is a sorted linked list; the upper levels only provide a fast entry point into it.
  • So two indexed relations are two sorted lists, and a join over them is traversal plus reconciliation.
  • Reconciliation is three cases: advance the smaller key, or on equality emit the cross product of the two runs and advance both.
  • Cost goes from multiplicative |R| × |S| to additive |R| + |S|, with the run cross-product as the one exception.
  • Index nested loop uses the descent; merge join uses the chain. Same structure, two different services.
