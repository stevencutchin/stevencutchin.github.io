Look ahead · what the engine actually does

Under the hood:
a relation as a B+tree

You've been treating a relation as a set of rows. The engine has to find those rows on a slow disk — fast, and in order.

The structure that makes WHERE key = … and ORDER BY cheap is the B+tree. This is a preview: enough to see the machine under the table.

Framing

A relation is logical; storage is physical

Everything so far has been logical: a relation is a set of rows, and WHERE picks some out. The DBMS still has to answer that query against bytes on a disk — and the disk is the slow part.

One structure makes the difference between reading a whole table and jumping straight to a row: the B+tree index. It's what PRIMARY KEY quietly builds for you.

This is a look ahead

The full treatment — cost models, node splitting, clustering vs. secondary indexes — is Unit 7. Today's goal is only to see how the relation you just designed becomes a tree, and why that's fast.

The one number that matters

A disk block read is roughly 100,000× slower than a memory access. Query cost is counted in block reads, not instructions. Fewer blocks touched = faster.

Step 1 · where the rows live

The relation on disk

A row becomes a record. Records are packed into fixed-size blocks (pages), typically 4–8 KB — and the block is the unit of disk I/O. You never read one row; you read the block it sits in.

A plain table with no ordering is a heap file: blocks in no particular order, rows appended wherever there's room.

Consequence

To read 1 row you read 1 block. To be sure you've found every matching row in a heap, you may have to read all of them.

Step 2 · the cost we want to kill

Finding one row is expensive

Ask a simple question of the heap:

SELECT * FROM STUDENT WHERE StudentID = 'S1027';

With no index, the engine does a full scan: read a block, check its rows, read the next, and so on. For a table of B blocks that's up to B block reads for one row.

At scale

A million rows might be 50,000 blocks. One equality lookup shouldn't cost 50,000 disk reads — and with an index, it costs about four.

Step 3 · the fix, in principle

Keep a map: key → where the row lives

An index is a second, ordered structure that maps each key value to the address of its record — exactly like the index at the back of a book maps a term to a page.

Because it's kept in sorted order, you can navigate it instead of scanning: a search rules out half the remaining keys at each step.

But a flat sorted list isn't enough

Binary search over a sorted file is fast to read but brutal to keep sorted — one insert shifts everything after it. We want a structure that's cheap to search and cheap to update.

The index is small and ordered; the data blocks stay put.

Step 4 · why this tree

Why a B+tree, not just any tree

The winning idea: make each tree node one disk block. Since a block holds hundreds of keys, each node has hundreds of children — a huge fanout.

High fanout makes the tree shallow, and it's kept balanced, so every search touches the same small number of levels — one block read per level.

The height payoff

A binary tree of a million keys is ~20 levels deep — up to 20 reads. A B+tree with fanout ~250 reaches a million keys in 3 levels, and a billion in 4–5.

Wide beats deep when every level costs a disk read.

Step 5 · the parts

Two kinds of node

Internal nodes are pure signposts: keys and child pointers, no data. Their only job is to route a search to the right leaf.

Leaf nodes hold every key value, each paired with a record pointer to the row's block. The leaves are chained left-to-right in sorted order.

The B+tree promise

All data pointers live at the leaves, and all leaves sit at the same depth. Balance is a guarantee, not luck — kept up as rows are inserted and deleted (the how is Unit 7).

Step 6 · the correspondence

Each row becomes one leaf entry

Here is the whole mapping in one sentence: every row of the relation contributes exactly one leaf entry — the value of the indexed column, paired with a pointer to that row's block.

  • Indexed column value → the search key in a leaf.
  • The row's location → the record pointer beside it.
  • Internal nodes are a sparse directory the engine builds over the sorted leaf keys — one routing key per child.

The rows never move. The B+tree sits beside the table as a fast way in.

Step 7 · the search that pays off

One equality lookup, block by block

Back to WHERE StudentID = 'S1027', now with the B+tree:

  1. Read the root. S1027 falls in its S1027–S1040 range → follow that child pointer. read 1
  2. Read that leaf. Find S1027; take its record pointer. read 2
  3. Read the data block the pointer names; return the row. read 3

3–4 reads, not thousands

And the upper levels are almost always cached in memory, so the real disk cost is often a single read. That's the whole game.

The B+tree's signature move

Ranges and ordering come for free

Because the leaves are a sorted linked list, a range query doesn't restart the search for each value:

… WHERE GPA BETWEEN 3.0 AND 3.5

Descend once to the first leaf at 3.0, then walk the leaf chain rightward, emitting rows, until you pass 3.5. ORDER BY on the indexed column is the same walk — the data is already in order.

Why not a hash index?

A hash gives O(1) equality lookups but scatters keys with no order — it can't do ranges or sorted scans at all. The B+tree does both, which is why it's the database default.

Wrap-up

What's under the hood

The mapping

  • Rows → records → blocks, the unit of disk I/O.
  • Each row → one leaf entry: (key, record pointer).
  • Internal nodes route; leaves hold all keys, sorted and chained.
  • Equality lookup ≈ tree height + 1 reads; ranges walk the leaf chain.

You've already been building these

PRIMARY KEY and UNIQUE create a B+tree automatically; CREATE INDEX builds one on any column. Height ≈ logfanout(N) — a handful of levels for any table you'll meet.
