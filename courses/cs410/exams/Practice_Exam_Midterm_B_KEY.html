Practice Exam — Answer Key

CS 410/510 — Databases · 90 points · 75 minutes

Work the practice exam closed-book in one timed sitting before you read this. Checking answers you have not yet attempted feels productive and teaches almost nothing.

Each question below gives the answer, the reasoning behind it, and how the points divide so you can score yourself honestly. Where a question has several correct formulations, the one shown is an example — if yours differs but computes the same thing, it is right. The Watch out boxes describe the mistakes that actually cost marks.

Part 1 (40 points): Issue Tracker Data Model

1.1 Reverse engineering 20 pts

Answer

Three entity types.

  • APP_USER — user_id (key), username, email, pw_hash, joined_on. Both username and email are additional candidate keys, since each is NOT NULL UNIQUE.
  • PROJECT — project_id (key), name, summary, created_on.
  • ISSUE — issue_id (key), title, body, opened_on.

Four relationships.

  • MEMBER_OF — M:N between APP_USER and PROJECT, carrying the descriptive attribute joined_on. project_membership is a junction table: in an E-R diagram it is a relationship, not a third entity. The giveaway is that its primary key is exactly the two foreign keys and it carries nothing else of its own but a timestamp.
  • REPORTED_BY — N:1 from ISSUE to APP_USER, with total participation on the ISSUE side: reporter_id is NOT NULL, so every issue has a reporter.
  • BELONGS_TO — N:1 from ISSUE to PROJECT, partial participation, because project_id is nullable: an issue need not sit in a project.
  • SUB_ISSUE_OF — a recursive 1:N relationship from ISSUE to itself. An issue has at most one parent and may have many children; partial on both sides, since parent_issue_id is nullable.

Reading the nullability tells you the shape of the world the schema allows: an issue can be a standalone report filed against a project, a sub-issue of another issue, both, or neither.

How the 20 points divide
  • 9 — three entity types with attributes and primary keys marked (3 each).
  • 4 — MEMBER_OF as an M:N relationship carrying joined_on.
  • 4 — REPORTED_BY and BELONGS_TO with correct N:1 cardinality, and their participation constraints.
  • 3 — the recursive SUB_ISSUE_OF relationship.
Watch out

The recursive relationship is the single most-missed item on this style of question. If you listed parent_issue_id as an ordinary attribute of ISSUE and drew no loop, you lost those 3 points. Any column that references its own table is a recursive relationship and must appear as one.

1.2 a Ten most prolific reporters 4 pts

Answer
SELECT u.user_id, u.username, COUNT(*) AS issue_count FROM app_user u JOIN issue i ON i.reporter_id = u.user_id GROUP BY u.user_id, u.username ORDER BY issue_count DESC LIMIT 10;

An inner join is right here: someone who has opened no issues is not a prolific reporter, so dropping them is what you want. After an inner join COUNT(*) and COUNT(i.issue_id) agree.

Graduate students. The grouping is expressible in relational algebra; ordering and "top 10" are not operators of the algebra, so write the aggregation and say so:

γ reporter_id ; COUNT(issue_id) → cnt ( issue )
Scoring · 4 pts
  • 2 — join and grouping by user.
  • 1 — the count in the select list.
  • 1 — ORDER BY … DESC with LIMIT 10.

1.2 b Twenty-five most recent sub-issues of dana's issues 4 pts

Answer
SELECT c.issue_id, c.title, c.opened_on FROM issue c JOIN issue parent ON c.parent_issue_id = parent.issue_id JOIN app_user u ON parent.reporter_id = u.user_id WHERE u.username = 'dana' ORDER BY c.opened_on DESC LIMIT 25;

The whole difficulty is the self-join. issue appears twice under two aliases: c is the child, which is what the query returns, and parent is the issue dana filed, which is what the WHERE clause tests. Once you see that two different rows of the same table play two different roles, the query writes itself.

Scoring · 4 pts
  • 2 — the self-join on c.parent_issue_id = parent.issue_id.
  • 1 — testing the username on the parent side.
  • 1 — ORDER BY opened_on DESC LIMIT 25.
Watch out

Filtering c.reporter_id by dana gives the sub-issues dana wrote, not the sub-issues written on her issues. It is a one-word difference in the query and a completely different result set. Read role-based questions twice: "replies to X's posts" and "replies by X" are not the same question.

1.2 c Five newest users 4 pts

Answer
SELECT user_id, username, joined_on FROM app_user ORDER BY joined_on DESC LIMIT 5;

"Newest" means most recent, so the sort is descending. Ascending would give you the five oldest accounts — the only real trap in the question.

Scoring · 4 pts
  • 2 — correct table and columns. 2 — DESC with LIMIT 5.

1.2 d Users who never opened an issue 4 pts

Answer — any of these three is fully correct:
-- outer join, then keep the rows that found no match SELECT u.user_id, u.username FROM app_user u LEFT JOIN issue i ON i.reporter_id = u.user_id WHERE i.issue_id IS NULL; -- correlated subquery SELECT user_id, username FROM app_user u WHERE NOT EXISTS (SELECT 1 FROM issue i WHERE i.reporter_id = u.user_id); -- set difference SELECT user_id, username FROM app_user WHERE user_id NOT IN (SELECT reporter_id FROM issue);

The third is safe here only because issue.reporter_id is declared NOT NULL. If that column could be NULL, a single NULL inside the subquery would make NOT IN return the empty set — the same three-valued logic that question 3.3 is about. The NOT EXISTS form has no such hazard, which is why experienced people reach for it by default.

Graduate students. This one is clean in relational algebra:

π user_id ( app_user ) − ρ user_id ← reporter_id ( π reporter_id ( issue ) )

The rename matters: set difference requires both sides to be union-compatible, so the projected column has to carry the same name.

Scoring · 4 pts
  • 4 — any of the three forms, correctly written.
  • Graduate students: full marks require the set difference, not a join rewritten in algebra notation.
Watch out

Writing WHERE i.issue_id IS NULL against an inner join returns nothing at all: an inner join never produces a NULL-padded row, so there is nothing for the test to find. The outer join is what manufactures the NULLs that the WHERE clause then looks for.

1.2 e Projects with at least three members 4 pts

Answer
SELECT p.project_id, p.name, COUNT(*) AS members FROM project p JOIN project_membership m ON m.project_id = p.project_id GROUP BY p.project_id, p.name HAVING COUNT(*) >= 3;

If you only need the id, grouping project_membership by itself is equally correct — the join exists to get the project's name into the output.

Scoring · 4 pts
  • 2 — grouping by project. 2 — the HAVING COUNT(*) >= 3 test.
Watch out

A count cannot go in WHERE. WHERE is evaluated row by row before any grouping happens, so there is no group yet to count. HAVING is the filter that runs after grouping. If you wrote WHERE COUNT(*) >= 3, the shape of your answer was right but the order of evaluation was not — and the database would reject the query outright.

Book: (1, writer 2, Tidewater), (2, writer 1, Quarry), (3, writer 1, Lantern). Author: (1, Mira, Peru), (2, Noor, Chile), (3, Otto, Brazil).

Watch out

The commonest error is answering with the three rows of 2c — quietly supplying a join condition the query never stated. That is exactly the misconception this question is built to expose. A comma join with no WHERE clause always returns every combination.

2 c … author JOIN book ON (author_id = writer_id) 4 pts

Answer — 3 rows, one per book.
nametitle

MiraLantern

Each book is matched to the author whose author_id equals its writer_id. Otto wrote nothing, and an inner join silently drops him — which is the entire difference between this question and 2e.

2 e Left outer join, grouped and counted 4 pts

Answer — 3 rows.
author_idnameCOUNT(book_id)
3Otto0
2Noor1
1Mira2

The outer join keeps Otto and pads the book columns with NULL. COUNT(book_id) counts non-null values only, so Otto's count is 0 and he sorts to the top.

The point of 2d and 2e together

Had the query said COUNT(*) instead of COUNT(book_id), Otto's row would report 1, not 0 — because COUNT(*) counts rows, and the outer join produced one padded row for him. COUNT(column) counts non-null values; COUNT(*) counts rows. On a query with an outer join those two are different numbers, and this pair of questions exists to find out whether you know which is which.

Scoring · 4 pts
  • 2 — Otto present. 1 — his count is 0, not 1 or NULL. 1 — ascending order.

Part 3 (8 points): Keys and Table Design

3.1 Why user_id beats username 2 pts

Answer — any two of:
  • Usernames change. People rename themselves. A primary key is copied into every table that references it, so one rename forces a cascading update across the whole database. A surrogate user_id is never updated because it never means anything.
  • It is wide. VARCHAR(100) against a 4-byte integer means larger index entries, fewer entries per B+tree page, lower fanout and a deeper tree — and every foreign key elsewhere carries a full copy of that string.
  • It carries meaning from outside the database. Anything with real-world significance is eventually subject to real-world change: policy on case-sensitivity, reserved names, reuse of a released name after an account closes.

Note what is not a reason: username is a perfectly valid candidate key. The question is about which candidate key to promote, not about legality.

Scoring · 2 pts
  • 1 per reason, correctly stated with its consequence. "It's a string" alone is not a reason — say what goes wrong.

3.2 Keys of project_membership 3 pts

Answer
  • Primary key: the composite (user_id, project_id).
  • Foreign keys: user_id → app_user(user_id); project_id → project(project_id).
  • The rule it enforces: a given user can join a given project at most once. It does not limit how many projects a user joins, or how many members a project has — only the pairing is unique.

Each key attribute is simultaneously part of the primary key and a foreign key on its own. That double role is the signature of a junction table implementing an M:N relationship, and joined_on is a descriptive attribute of the relationship rather than of either entity.

Scoring · 3 pts
  • 1 — composite primary key. 1 — both foreign keys. 1 — the uniqueness rule stated correctly.
Watch out

Naming user_id alone as the primary key would mean each user could join only one project ever — which defeats the entire purpose of the table.

3.3 Why title <> 'crash' hides NULL rows 3 pts

Answer

What the query evaluates. For a row whose title is NULL, the expression NULL <> 'crash' is neither true nor false — it is UNKNOWN, SQL's third truth value. A WHERE clause keeps only rows for which the predicate came out TRUE, so rows evaluating to UNKNOWN are discarded just as firmly as rows evaluating to FALSE.

Which reading of NULL this reflects. The "value is not known" interpretation. If the title exists but was never recorded, then whether it differs from 'crash' is simply unanswerable — the missing value might be 'crash' and might not. SQL declines to guess and returns UNKNOWN rather than committing to an answer it has no basis for.

The rewrite. Ask the second question explicitly:

SELECT * FROM issue WHERE title <> 'crash' OR title IS NULL;

IS NULL is a separate test precisely because it asks about the marker itself rather than about the value behind it, so it always returns a definite true or false. PostgreSQL also offers WHERE title IS DISTINCT FROM 'crash', which does the same job in one operator.

Scoring · 3 pts
  • 1 — the comparison yields UNKNOWN, and WHERE keeps only TRUE.
  • 1 — naming the "value is not known" reading.
  • 1 — a rewrite that brings the NULL rows back.
Watch out

Answering "the comparison returns FALSE" loses a point. FALSE and UNKNOWN are genuinely different: under NOT they behave differently — NOT FALSE is TRUE, while NOT UNKNOWN is still UNKNOWN — which is why you cannot escape the problem by negating the condition.

Part 4 (22 points): B+trees, Indexes, and Normalization

4.1 Range scan over the B+tree 4 pts

Root separators 20 | 35 | 52 over leaves [6 12 17] [20 26 31] [35 44 49] [52 60 71]; query WHERE weight BETWEEN 26 AND 49.

Four pages read, and a final leaf that yields nothing but the key that stops the scan.

Answer
  1. Root → leaf 2 → leaf 3 → leaf 4. The descent carries the lower bound 26: at the root, 26 is not below the separator 20 but is below 35, so the second pointer is taken into leaf 2, landing on the first entry at or after 26. Leaves 3 and 4 follow through the next-leaf pointers, never through the root.
  2. Four index pages.
  3. 52 ends the scan, and it is on leaf 4. The upper bound 49 happens to be the last key of leaf 3, so leaf 3 runs out without the walk ever meeting a key that fails. A leaf running out is not evidence that the range has ended — the next leaf might open with more qualifying keys. The only way to establish that the range is finished is to follow the next-leaf pointer and read one key, and that key, 52, is the first one that exceeds 49. Leaf 4 therefore costs a page read while contributing no rows at all.

Qualifying keys: 26, 31, 35, 44, 49 — five rows. Note that 20 sits on leaf 2 and is read into memory with the rest of the page, but fails the lower bound and is not part of the answer.

Scoring · 4 pts
  • 1.5 — the four nodes named in the right order.
  • 1 — the count of four.
  • 1.5 — identifying 52 on leaf 4, and explaining why that leaf must be read.
Watch out

If you answered "three pages, stopping at 49", you assumed the scan can tell it is finished when a leaf ends. It cannot. This is the same principle as the ordinary stopping rule — the walk always needs one comparison that fails — and here that comparison simply happens to live on the following page. Whenever a range's upper bound lands on a leaf boundary, expect one extra page read.

The other frequent error is a second root-to-leaf descent to find the upper bound. There is never one: you descend for the start of a range and discover its end by walking into it.

4.2 Fanout and height 2 pts

Answer

Why it stays shallow. Each index page holds about 250 entries, so every extra level multiplies the number of reachable entries by roughly 250 rather than by 2. Depth therefore grows as the logarithm of the table size in base 250: three levels reach 2503 ≈ 15.6 million, which is not enough for 50 million rows, while four reach 2504 ≈ 3.9 billion — far more than needed. The table would have to grow about 250-fold before a fifth level became necessary, which is why B+tree depth is nearly constant across databases of wildly different sizes.

What the lookup costs. One page read per level: 4 index page reads to reach the leaf entry. Add one more to fetch the row itself if the index is secondary and does not already carry every column the query needs. In practice the root and the level below it are almost always sitting in the buffer pool, so the measured cost is usually lower.

Scoring · 2 pts
  • 1 — the fanout argument. An arithmetic demonstration (2503 against 2504) earns it just as well as the word "logarithmic".
  • 1 — the number 4, one read per level.

4.3 Index for a date range, and for YEAR(opened_on) 3 pts

Answer (a)

BTREE, on opened_on.

BETWEEN is a range test, and only an ordered index can answer one: the engine descends to the first entry at or after '2026-01-01', walks the leaf chain, and stops one key past '2026-03-31'. A HASH index serves equality alone, because hashing deliberately destroys order — there is no "next" entry to follow. FULLTEXT builds an inverted index over words and has nothing to say about timestamps.

Answer (b)

No. YEAR(opened_on) wraps the column in a function. The index stores opened_on itself, not the result of calling YEAR on it, so the engine has no value it can descend the tree with. The index is simply ignored and the query falls back to a full table scan — with no error and no warning, which is what makes this failure so easy to miss in practice.

Two ways out. Rewrite the predicate so the column stands bare, which the existing index serves —

WHERE opened_on >= '2026-01-01' AND opened_on < '2027-01-01'

— or build a functional index on the expression YEAR(opened_on) itself, if the query cannot be changed.

Scoring · 3 pts
  • 1 — BTREE on opened_on.
  • 1 — why: ranges need ordering, which hash indexes do not provide.
  • 1 — "no" for part (b), with the reason the index cannot be used.
The rule worth memorising

A predicate is sargable — searchable by argument — when the engine could find the first matching entry by descending the tree with a value it already has. Put the column inside any function or expression and that becomes impossible. Keep the column bare on one side of the comparison and do the arithmetic on the other side.

4.4 Index for MATCH (title, body) AGAINST ('deadlock') 3 pts

Answer

FULLTEXT, on (title, body) together — one index covering both columns, not an index on each.

MATCH … AGAINST looks for a word inside a block of text. A B+tree orders whole values, so it can answer a prefix test like LIKE 'dead%' but has no way to find a word buried in the middle of a body; a hash index is limited to equality on the entire value, which would mean a body consisting of exactly the word "deadlock". A full-text index inverts the relationship, storing each distinct word with the list of rows containing it, so a word lookup becomes a direct probe.

The column list is part of the answer: MATCH must name exactly the set of columns its full-text index was built over, so FULLTEXT(title, body) is required here. Separate indexes on title and on body will not satisfy this query.

Scoring · 3 pts
  • 1 — FULLTEXT. 1 — both columns in a single index. 1 — the reasoning about word-level search.

4.5 Normalization of R(Technician, Machine, Workshop, Specialty, Shift) 10 pts

FDs = { Technician → Specialty ; Technician, Machine → Workshop ; Workshop → Shift }

4.5.1 Candidate keys 2 pts

Answer

{Technician, Machine} — and it is the only candidate key.

Start from a useful shortcut: Technician and Machine never appear on the right-hand side of any dependency, so nothing can ever derive them. Any key must therefore contain both. Now test whether those two alone suffice:

{T, M}+ = {T, M}     → add Specialty  (Technician → Specialty)     → add Workshop   (Technician, Machine → Workshop)     → add Shift      (Workshop → Shift)     = {T, M, Specialty, Workshop, Shift} = R

The closure reaches every attribute, so {Technician, Machine} is a key. It is minimal because neither half works alone: {Technician}+ = {Technician, Specialty} and {Machine}+ = {Machine}. Since every key must contain both attributes and those two already suffice, there is no other candidate key.

The prime attributes are therefore Technician and Machine. Workshop, Specialty and Shift are all non-prime — remember this for 4.5.4.

Scoring · 2 pts
  • 1 — the correct key. 1 — the closure computation shown.

4.5.2 A non-minimal superkey 2 pts

Answer

For example {Technician, Machine, Workshop}.

It is a superkey because it contains {Technician, Machine} and so determines every attribute of R. It is not minimal because Workshop can be removed and what remains still determines everything — a minimal superkey is precisely what "candidate key" means. {Technician, Machine, Shift} and the full attribute set work equally well as examples.

Scoring · 2 pts
  • 1 — a genuine superkey containing both key attributes. 1 — saying why it is not minimal.

4.5.3 Is R in BCNF? 2 pts

Answer

No — and there are two separate violations. BCNF demands that the left-hand side of every nontrivial dependency be a superkey. Test all three:

  • Technician, Machine → Workshop — the left side is the candidate key. Fine.
  • Technician → Specialty — {Technician}+ = {Technician, Specialty}, which is not all of R, so Technician is not a superkey. Violates BCNF.
  • Workshop → Shift — {Workshop}+ = {Workshop, Shift}, also not all of R. Violates BCNF.
Scoring · 2 pts
  • 1 — the verdict "no". 1 — naming both violating dependencies; finding only one earns half.
Watch out

Check every dependency, not just the first one that looks suspicious. The question asked for all violations, and Workshop → Shift is easy to overlook because neither of its attributes is part of the key — which is exactly what makes it a violation.

4.5.4 Is R in 3NF? If not, decompose 4 pts

Answer

No, R is not in 3NF either.

3NF is more forgiving than BCNF: a dependency X → A is acceptable if X is a superkey or A is a prime attribute. From 4.5.1 the prime attributes are Technician and Machine, so test the two dependencies that failed BCNF:

  • Technician → Specialty — Technician is not a superkey, and Specialty is not prime. Both escape clauses fail, so this violates 3NF.
  • Workshop → Shift — Workshop is not a superkey, and Shift is not prime. This violates 3NF too; it is a textbook transitive dependency, since the key determines Workshop and Workshop in turn determines Shift.

Decomposition. The given FDs are already a minimal cover, so apply 3NF synthesis — one relation per dependency:

R1 ( Technician, Specialty ) -- Technician → Specialty R2 ( Technician, Machine, Workshop ) -- Technician, Machine → Workshop R3 ( Workshop, Shift ) -- Workshop → Shift

R2 contains the candidate key {Technician, Machine}, so no additional relation has to be bolted on to preserve it.

Lossless. Join them back in stages. R1 ∩ R2 = {Technician}, which is the key of R1, so that join is lossless. The result then meets R3 on {Workshop}, which is the key of R3, so that join is lossless as well. Whenever the shared attributes form a key of one of the two relations being joined, no spurious tuples can appear.

Dependency-preserving. Each of the three original dependencies lives entirely inside one relation — Technician → Specialty in R1, Technician, Machine → Workshop in R2, Workshop → Shift in R3 — so every constraint can be enforced without joining anything.

A bonus worth noticing: each fragment's only dependency has that fragment's own key on the left, so all three are in BCNF as well. This decomposition gets BCNF and dependency preservation at once, which is not always possible — sometimes you must choose.

Scoring · 4 pts
  • 1 — "no", with the reason: a non-prime attribute depending on a non-superkey, or equivalently a transitive dependency.
  • 2 — the three-relation decomposition.
  • 1 — justifying lossless join and dependency preservation.
Watch out

Stopping after splitting off Specialty leaves Workshop → Shift still violating 3NF inside R2 — a decomposition that fixes one violation and ignores another is not in 3NF. Always re-check each fragment you produce.
