Part 1  ·  Anomalies 12 points

The site stores everything in one relation:

BOOKMARK_FEED(
  username, email, joined,
  url, title, description, saved_on, private,
  tag,
  cached_on, cache_status, page_bytes
)

The universal relation used throughout this assignment.

Each row records one tag applied to one bookmark. A user has an email address and a join date. A bookmark belongs to a user, has a title, description, save date, and a private flag, and carries zero or more tags — one row per tag. The cache is a single shared copy of each web page: whatever the URL, there is one cache attempt, with one date, one status (success, not found, server failed), and one page size.

Using this relation, give a concrete example of each of the three update anomalies below. An example means naming the specific attributes and rows involved — not a general description of the anomaly type. For each, name the informal design guideline from Ch. 14 that the schema violates.

  1. An insertion anomaly: something true about the world that this schema cannot record.
  2. A deletion anomaly: a deletion that destroys unrelated information as a side effect.
  3. A modification anomaly: a single real-world change that forces many rows to be updated, and what goes wrong if one is missed.

Then state, in one sentence each, which two of the four informal guidelines (clear semantics, no redundant updates, few NULLs, no spurious tuples) this schema most clearly violates.

Deliverable

Three worked anomaly examples with named attributes, each tied to a guideline, plus the two-sentence summary.

Part 2  ·  Functional Dependencies 22 points

The following functional dependencies hold on BOOKMARK_FEED:

F1.  username            →  email, joined
F2.  email               →  username
F3.  email               →  joined
F4.  username, url       →  title, description, saved_on, private
F5.  url                 →  cached_on, cache_status, page_bytes
F6.  username, url       →  page_bytes

The given FD set F. Email addresses are unique to one account.

2.1   Closures and Candidate Keys — 10 points

Compute the following attribute closures under F, showing which FD you applied at each step:

  • {username} +
  • {url, tag} +
  • {email, url} +

Then find every candidate key of BOOKMARK_FEED. For each one, show that it is a superkey and that no proper subset of it is. State which attributes are prime.

Deliverable

Three closures with justified steps, all candidate keys with minimality arguments, and the set of prime attributes.

2.2   Minimal Cover — 8 points

Compute a minimal cover of F. Work in the standard three stages and show the result of each: put every FD in canonical form with a single attribute on the right; remove extraneous attributes from left-hand sides; remove redundant FDs.

There is slack in F, and more than one right answer

F has redundancy built into it deliberately. Written in canonical form it runs to twelve dependencies; a correct minimal cover has ten. If nothing dropped out, recheck the redundancy stage — and for each FD you remove, say which surviving FDs make it redundant.

Minimal covers are not unique. Two students can remove different dependencies and both be right, so the justification is what is being graded, not a match against a specific answer.

Deliverable

The minimal cover, with the three stages shown separately and each removal justified.

2.3   Armstrong's Axioms — 4 points

Prove that username, url → cache_status follows from F using Armstrong's axioms alone. Name the axiom — reflexivity, augmentation, or transitivity — used at every step. Derived rules such as union or decomposition are allowed only if you first derive them from the three axioms.

Deliverable

A step-by-step derivation with each axiom named.

Part 3  ·  Normalization 26 points

3.1   Highest Normal Form — 6 points

State the highest normal form BOOKMARK_FEED satisfies, and prove it. Your proof must name a specific dependency that violates the next normal form up, and say whether that violation is a partial or a transitive dependency.

Deliverable

The normal form, the violating dependency, and its classification.

3.2   Decomposition to 3NF — 10 points

Using the 3NF synthesis algorithm and the minimal cover from 2.2, decompose BOOKMARK_FEED into a set of 3NF relations. For each resulting relation give its attributes, its primary key, and any foreign keys. State explicitly where the algorithm required you to add a relation to preserve a candidate key, and where one relation was subsumed by another and dropped.

Check the result against your instincts

When you are done, compare your schema to the one you would have drawn straight from the description in Part 1 — the four entities a reasonable designer would have picked in HW1. If the algorithm did its job, you should recognize the output. Say in a sentence or two whether it matches, and note any difference.

Deliverable

The 3NF schema with keys and foreign keys, the two algorithm notes, and the comparison.

3.3   BCNF — 6 points

Tags on the site are organized into categories — python and rust are in the language category, tutorial and reference are in the kind category. Every tag belongs to exactly one category, and a user applies at most one tag from any given category to any given bookmark. That gives:

BOOKMARK_TAG(username, url, tag, tag_category)

G1.  tag                            →  tag_category
G2.  username, url, tag_category    →  tag

A focused relation for the BCNF question. Treat G as its complete FD set.

Answer each of the following:

  1. Find both candidate keys of BOOKMARK_TAG.
  2. Show that this relation is in 3NF.
  3. Show that it is not in BCNF, naming the offending dependency.
  4. Decompose it into BCNF relations.
  5. Name the functional dependency your decomposition no longer preserves, and explain what the database can no longer enforce without a join.
Deliverable

Both keys, the 3NF and BCNF arguments, the decomposition, and the lost dependency with its practical consequence.

3.4   Lossless Join — 4 points

Here are two proposed decompositions of BOOKMARK_FEED into two relations each. Exactly one is lossless.

Decomposition A
  A1(username, email, joined, url, title, description, saved_on, private)
  A2(url, tag, cached_on, cache_status, page_bytes)

Decomposition B
  B1(username, email, joined)
  B2(username, url, title, description, saved_on, private,
     tag, cached_on, cache_status, page_bytes)

For each decomposition, apply the binary lossless-join test: find the common attributes, compute their closure, and determine whether they form a superkey of at least one of the two relations. State which decomposition is lossless and which is lossy. For the lossy one, describe the spurious tuples a join would produce — what false fact about the world would appear in the result.

Graduate students (CS 510)

Also show the lossy case formally with the chase test: build the tableau, apply the FDs in F until no further change is possible, and state what the final tableau proves.

Deliverable

Both tests worked through, the verdict on each decomposition, and a described spurious tuple. CS 510 students also give the chase tableau for the lossy decomposition.

Part 4  ·  Storage and Index Selection 28 points

Work from your 3NF schema from 3.2 for the rest of the assignment. The site runs on a single disk with the following parameters, and the relations have the following statistics:

Block size                        4,096 bytes
Block pointer                         6 bytes
Record pointer                        8 bytes

BOOKMARK    8,000,000 records     record size  200 bytes
USER          200,000 records     record size   80 bytes
CACHE       3,000,000 records     record size  120 bytes
SUBSCRIPTION 2,000,000 records    record size   40 bytes

username is 20 bytes.  saved_on is 8 bytes.

Assume unspanned record organization and fully packed nodes unless a question says otherwise.

SUBSCRIPTION(subscriber, publisher) records that one user follows another; both attributes reference USER. The site serves this workload, which is the same set of questions the bookmark site has to answer for its users:

W1.  For one user, their bookmarks ordered by save date, newest first.
W2.  The 10 users with the most bookmarks.
W3.  The number of new users in each year.
W4.  The users with more than 2 bookmarks.
W5.  The number of users having more than 1,000 subscribers.
W6.  For one user, each tag they have used and how many bookmarks carry it.
W7.  Users with no followers.

The query workload. W1 and W6 run constantly; W2–W5 run once a night; W7 runs monthly.

4.1   File Sizing — 4 points

Compute the blocking factor and the number of blocks for BOOKMARK and for USER. Show the division and state how you rounded at each step, and why that rounding direction is the correct one.

Deliverable

Blocking factor and block count for both relations, with rounding justified.

4.2   The Cost of W1 — 10 points

Query W1 retrieves the bookmarks of one specific user. Estimate the number of block accesses required under each of these three file organizations, stating your assumptions:

  1. BOOKMARK as an unordered heap file, with no index.
  2. BOOKMARK as a file sorted on username, searched with binary search.
  3. BOOKMARK as a heap file with a secondary B+-tree index on username. Assume the index has 3 levels and that each matching record sits in a different block.

The average user has 40 bookmarks. Rank the three organizations by cost. One of the results is likely to surprise you: explain in two or three sentences why the index loses to the organization it loses to, and name the one change to the index that would make it the clear winner.

Deliverable

Three cost estimates with assumptions, a ranking, and the explanation of the surprising result.

4.3   B+-Tree Fanout and Height — 8 points

Build the secondary B+-tree index on BOOKMARK(username) from the parameters above.

  1. Compute the order p of an internal node — the largest number of block pointers that fits in one block alongside its keys. Give the inequality you solved.
  2. Compute the leaf order p_leaf, remembering that a leaf holds key/record-pointer pairs plus one pointer to the next leaf.
  3. There are 200,000 distinct usernames. Compute the number of levels in the tree, assuming nodes are fully packed, and show the block count at each level.
  4. Recompute the number of levels assuming the more realistic 69% node occupancy. Does the height change?
Deliverable

Both orders with their inequalities, the level counts at full and 69% occupancy, and whether the height changed.

4.4   Index Selection — 6 points

Propose an index set for the whole workload W1–W7. For each index you propose, give the relation and attributes, the type (primary, clustering, or secondary), which queries it serves, and a one-sentence justification. You may propose at most five indexes in total.

Then name one index that looks obviously useful but which you have deliberately not proposed, and explain the cost that rules it out.

Graduate students (CS 510)

Also estimate the block accesses for W7 (users with no followers) under two strategies: a nested-loop anti-join against SUBSCRIPTION, and a scan of a secondary index on SUBSCRIPTION(publisher). State which wins and by roughly what factor.

Deliverable

At most five indexes with type and justification, plus the rejected index with its cost. CS 510 students also give the two W7 estimates with a verdict.

Part 5  ·  Denormalizing Against the Workload 12 points

W2, W4, and W5 all count things: bookmarks per user, and subscribers per user. On the 3NF schema every one of them requires aggregating a multi-million-row relation. A colleague proposes adding two attributes to USER:

USER(username, email, joined, bookmark_count, subscriber_count)

Write a short analysis — roughly 300–500 words — arguing for or against this change. A good answer is specific about this schema and this workload, not about denormalization in general. Address all four of the following:

  1. Whether the change breaks a normal form at all. State the functional dependencies that now hold on USER, decide whether it is still in BCNF, and — if no normal form is violated — say precisely what kind of constraint is being violated and why FD-based normalization cannot express it.
  2. Which anomaly from Part 1 it reintroduces, with a concrete example of the database going wrong.
  3. What it costs to maintain: name every operation that must now update these attributes, and say what has to be true of those updates for the counts to stay correct.
  4. Under what workload mix you would ship it anyway. Give the rough read/write ratio or query frequency at which your answer flips, and say which of W1–W7 pushed you there.

There is no expected verdict

Both conclusions earn full marks. What is being graded is whether the argument is grounded in the dependencies you derived in Part 2 and the costs you computed in Part 4 — a defended "yes" beats an undefended "no".

Deliverable

A 300–500 word analysis addressing all four points, with a stated verdict.
